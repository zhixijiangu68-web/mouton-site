Windows のセキュリティのログには、監査ポリシーで決めたことしか残らない

ログの種類、監査ポリシー、4624・4625 とログオンの種類、4672・4688・4720・1102・7045、Sysmon、SOC での見方と SIEM への送り方を、Microsoft の文書と公開の検知ルールで確かめた

約12分更新日 2026年11月13日

Windows は、ログオンやプロセスの起動のような出来事を、番号（イベント ID）つきでイベントログに書く。何が残るかは監査ポリシーと Sysmon の設定で決まり、記録の対象にしていない出来事は残らない。SIEM の記事で触れた 4624・4625 と、検知ルールの記事の 4720・1102 を、ここで一つずつ読む。Linux の側はLinux のログの記事、NTLM の 4776 はNTLM の記事、7045 を遠隔操作ツールの悪用の手がかりにする例はRMM の記事に書いた。

イベントログは、ログの名前とイベント ID で探す

Windows の基本のログは三つある。Application はアプリケーションが書く出来事、Security はログオンの成功と失敗やファイルの操作のような監査の出来事、System はドライバーの読み込みの失敗のような OS の部品の出来事を残す。ファイルは、既定では %SystemRoot%\system32\winevt\logs\ の下に置かれる[1]。

Windows Vista でイベントログの仕組みが作り直され、出し手（プロバイダー）が自分のログ（チャネル）を定義できるようになった。チャネルには Admin・Operational・Analytic・Debug の四つの種類がある[1][2]。Sysmon は Microsoft-Windows-Sysmon/Operational のチャネルに書く[3]。

一つのイベントには、出し手、イベント ID、時刻、端末名、チャネルと、イベントごとの項目（EventData）が入る。Splunk が公開している 4624 の見本では、出し手が Microsoft-Windows-Security-Auditing、チャネルが Security で、ユーザー名やログオンの種類は EventData の中にある[4]。番号はログと出し手ごとに決まるので、ログの名前と組にして読む。

何を残すかは、監査ポリシーで決まる

Security のログに何が残るかは、監査ポリシーで決まる。Microsoft の「Events to Monitor」は、監査に関わるグループポリシーの多くが既定で「未構成」で、残る出来事は Windows の版や種類で変わると書き、Advanced Audit Policy Configuration で監査を設定するよう勧めている[5]。

Windows Vista と Windows Server 2008 から、監査の大きな分類の下に細かい分類（サブカテゴリー）ができ、それぞれで成功・失敗・両方を選べるようになった。Logon の分類の出来事は、ログオンされた側の端末に残る。共有フォルダーへのネットワーク越しのログオンなら、共有を持つ端末の側だ。ドメインのアカウントの資格情報の確かめ（Credential Validation）は、ドメインコントローラーに残る[6]。

いま効いている設定は auditpol /get /category:* で見られる。グループポリシーの画面は有効な監査の状態を正しく表さないことがあり、auditpol は正しく表すと Microsoft は書いている[6][7]。細かい分類の設定は、古い基本の監査ポリシーで上書きされることがあり、上書きされると 4719 が残る[8]。

4624 は成功、4625 は失敗。ログオフは 4634 と 4647

ログオンの記録の中心は、4624（アカウントがログオンした）と 4625（ログオンに失敗した）だ。ログオフは 4634（ログオフした）と 4647（利用者がログオフを始めた）、資格情報を明示して使ったログオンの試みは 4648、アカウントのロックアウトは 4740 で残る[5]。

4624 で読む主な項目は、ログオンしたアカウント（TargetUserName）、ログオンの種類（LogonType）、相手のアドレス（IpAddress）と端末名（WorkstationName）、認証の方式（AuthenticationPackageName）、ログオン ID（TargetLogonId）だ[4]。Microsoft の 4624 の説明では、ログオン ID は、同じ ID を持つ近くの出来事（たとえば 4672）と結びつけるための値とされている[9]。

4625 には、失敗の理由が Status と SubStatus のコードで入る[4]。公開の検知ルール集 Sigma には、無効にされたアカウント（0xC0000072）や、許されていない端末から（0xC0000070）のような、ふだんは出にくい理由の失敗を拾うルールがある[10]。

ログオンの種類で、どう入ったかが分かる

4624 と 4625 の LogonType は、ログオンのしかたを表す番号で、Windows の SECURITY_LOGON_TYPE の値に合う[11]。

主なログオンの種類（SECURITY_LOGON_TYPE）
番号名前意味
2Interactive対話型のログオン
3Networkネットワーク越しのログオン
4Batchバッチの処理のためのログオン
5Serviceサービスのアカウントのログオン
7Unlock画面のロックの解除
8NetworkCleartext平文の資格情報によるネットワーク越しのログオン
9NewCredentials今のトークンを複製し、外への接続にだけ別の資格情報を使う

3 は、共有フォルダーを開くようなネットワーク越しのログオンで、共有を持つ側に残る[6]。10 はリモートデスクトップで、Microsoft はリモートデスクトップによるログオンを「リモートの対話型」と呼んでいる[12]。MITRE の分析の例 CAR-2016-04-005 も、「4624 で LogonType が 10」をリモートデスクトップのログオンとして拾い、許された端末からかを比べる[13]。

4672 は管理者級の権限、4720〜4756 はアカウントとグループの変更

4672 は、新しいログオンに特別な権限が割り当てられたことを表す[5]。特別なログオンは、管理者と同じ強さの権限を持つログオンのことだ[6]。Splunk の説明では、4672 は管理者の権限を持つ利用者のログオンで残り、権限の一覧が PrivilegeList に入る[4]。4624 とログオン ID で結べば、権限の強いログオンだけを取り出せる[9]。

アカウントの作成は 4720、削除は 4726、セキュリティのグループへのメンバーの追加は、グローバルのグループが 4728、ローカルのグループが 4732、ユニバーサルのグループが 4756 だ[5]。JPCERT/CC の調査の道具 LogonTracer も、これらの番号を扱う[14]。Sigma には、ローカルの Administrators のグループ（SID が S-1-5-32-544）へのメンバーの追加を 4732 で拾うルールがあり、正規の管理の作業を誤検知の候補に挙げている[10]。

「Events to Monitor」は、重さ「高」は1件でも調べ、「中」と「低」は思いがけないときや数がふだんを大きく超えたときに調べるとし、4624・4625・4672・4688・4720・4732 を「低」、監査ポリシーの変更（4719）を「高」としている[5]。

4688 は、設定しなければコマンドラインを残さない

4688 は、新しいプロセスが作られたことを表す。残すには Detailed Tracking の分類の Audit Process Creation を有効にする必要があり、既定は未構成だ[8]。

コマンドラインまで残すには、さらに Include command line in process creation events を有効にする。既定では有効になっていない。有効にすると、すべてのプロセスのコマンドラインが平文で Security のログに入る[8]。Splunk の 4688 の見本では、起動したプログラム（NewProcessName）、親のプログラム（ParentProcessName）、コマンドライン（CommandLine）が並ぶ[4]。

Microsoft は、有効にすると Security のログを読める人なら誰もがコマンドラインを読め、そこにはパスワードや利用者のデータが入りうると注意している[8]。残すかどうかは、ログを読める人をしぼることと一緒に決める。

Sysmon は、プロセスと通信を細かく残す

Sysmon（System Monitor）は Sysinternals の道具で、サービスとドライバーとして動き、出来事を Windows のイベントログに書く。2026年9月10日に公開された版は 15.22 だ[3]。

プロセスの起動（イベント ID 1）には、本人と親のプロセスのコマンドライン、実行ファイルのハッシュ、ProcessGuid が入る。ProcessGuid は、Windows がプロセス ID を使い回しても出来事をつなげるための値だ。ほかに、ネットワークの接続（3）、ファイルの作成（11）、レジストリの値の書き込み（13）、DNS の問い合わせ（22）、ファイルの削除（23）などがある。3 は既定では残らない[3]。

何を残すかは XML の設定ファイルで、出来事の種類ごとに含める・除くを決める。時刻は UTC で入る。Sysmon は出来事を分析せず、攻撃者から自分を隠そうともしないので、分析は SIEM の側でする[3]。

新しいサービスとログの消去は、それだけで目を向ける

サービスの追加は、System のログに 7045（出し手は Service Control Manager）として残り、サービスの名前（ServiceName）、実行ファイルのパス（ImagePath）、起動の種類（StartType）、動かすアカウント（AccountName）が入る[4]。Security のログの 4697 も、サービスのインストールを表す[5]。MITRE ATT&CK の検知の例（DET0552）は、C:\Users\ や C:\Temp\ のようなふだん使わない場所の実行ファイルを目印にしている[15]。Sigma にも、7045 の ImagePath に一時フォルダーのパスなどが入るものを拾うルールがある[10]。

Security のログを消すと 1102（監査のログが消された）が残り、「Events to Monitor」での重さは「中〜高」だ[5]。ほかのログを消したときは、System のログに 104 が残る[10]。MITRE の CAR-2016-04-002 は、ふだんの運用でログが消されることは考えにくいとし、ログを1か所に集めておけば痕跡を消すのがずっと難しくなると書いている[13]。

SOC では、数と時刻と前後の出来事で見る

1件では判断しにくい出来事も、数・時刻・前後の出来事を合わせると意味が出る。MITRE ATT&CK の検知の例は次のとおりだ[15]。

  • 失敗の連続：同じか似たアカウントへの 4625 が、一つか複数の送り元から続く（パスワードの推測）。一つか少数のパスワードで、多くのアカウントに失敗が広がる（パスワードスプレー。4625・4771・4648）
  • ふだんと違うログオン：見慣れないログオンの種類や、時刻・場所の食い違い。ローカルのアカウントが業務時間の外に使われる（4624・4648・4672）
  • リモートデスクトップのあとの動き：リモートデスクトップのログオンの直後（例として5分）に、cmd.exe や powershell.exe のようなプロセスが動く

深夜の管理者のログオンは、時刻だけでは決められない。夜の保守の作業もあるので、ATT&CK は業務時間の幅や、リモートデスクトップを使う人の範囲を、環境に合わせて調整する項目にしている[15]。Splunk の公開ルールには、ドメインコントローラーの 4776 で、存在しないユーザー名での失敗（Status が 0xc0000064）が一つの端末からふだんより大きく増えたことを拾うものもある[16]。失敗のあとの成功を見るルールの形は、検知ルールの記事に書いた。

SIEM へは、消される前に送る

端末の中のログは、その端末で消せる。だから、出来事が起きたら端末の外へ送っておく。

Windows には、ほかの端末のイベントを受け取って集める仕組み（Windows Event Collector）がある。送る側をグループポリシーで設定する「送る側から始める購読」と、送る側を全部指定する「集める側から始める購読」があり、転送されたイベントは中身を失わずに集める側のログに入る[17]。Sysmon の文書は、Windows Event Collection か SIEM のエージェントで集めて分析するよう書いている[3]。

Splunk では、Security と System のログは Splunk Add-on for Microsoft Windows、Sysmon のログは Splunk Add-on for Sysmon を使い、XML の形（sourcetype が XmlWinEventLog）で取り込む[4]。どのログから SIEM に入れるかの順は、SIEM の記事に書いた。

自分の環境で確かめる

イベントログは、自分の Windows の端末か、自分で作った演習の仮想マシンで見られる。他人の端末や、許可のない環境では試さない。

監査の設定は auditpol /get /category:* で一覧になる[6]。ログの一覧は wevtutil el、Security のログの新しい5件は wevtutil qe Security /c:5 /rd:true /f:text で読める[18]。PowerShell なら Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625} で、失敗したログオンだけを取り出せる。管理者として動かさないと、ログを読めないというエラーが出ることがある[19]。サインインの画面で違うパスワードを入れてから、4625 が残ったか、LogonType がいくつかを見る。

Sysmon は、演習用の仮想マシンに sysmon -accepteula -i で入れられる。既定の設定ではネットワークの接続（3）は残らないので、残すには設定ファイルを使う[3]。入れたら、Sysmon/Operational のログのイベント ID 1 に、親のプロセスとコマンドラインが入っているかを見る。

  • SIEM は攻撃を止めない。ログをつなげて、人に知らせる仕組みだ

    SIEM がするのは、集める・そろえる・つなげる・知らせる・残すまで。止めるのは SOAR などの別の仕組みと人。どのログを入れるかで、見えるものが決まる。

    HTTP は一つの要求に一つの応答を返し、要求どうしを覚えていない。前の要求とのつながりは Cookie が運ぶので、Cookie の属性と HTTPS が守りの土台になる。アクセスログの一行から読めることと、SIEM で見る観点もまとめた。
