ファイアウォールは、通すものだけを書いて残りを止める。穴は、ルールの順番と範囲の書き違いから開く

アドレス・ポート・プロトコルで決める仕組み、状態を覚える方式、ルールの順番、既定で拒否、出ていく通信、ログを、RFC と公式の文書で確かめた

約12分更新日 2026年11月7日

ファイアウォールは、パケットの送り元と宛先のアドレス、ポート、プロトコルを見て、通すか止めるかを決める仕組みだ。ルールは、通すものだけを書いて残りを止める「既定で拒否」が基本で、入ってくる通信と出ていく通信の両方に当てる。この記事は、IP アドレスの記事の許可リストの話と、TCP・UDP の記事のポートの話から広げた。例のアドレスは文書用の範囲とプライベートアドレスだけを使い、試すのは自分の機器の中だけにする。

ファイアウォールは、アドレスとポートとプロトコルで決める

ファイアウォールが手がかりにするのは、主にパケットの頭（ヘッダー）に書かれた送り元と宛先のアドレス、ポートの番号、プロトコルだ。インターネットのセキュリティの用語集 RFC 4949 は、ファイアウォールを、二つのネットワークのつなぎ目に置き、内側のネットワークに出入りする通信を制限して、外側からの脅威から守る関門だと定義している[1]。同じ用語集は、決まりに従ってパケットを通すかどうかを決めるルーターを「フィルタリングルーター」と呼び、その決まりは主に送り元と宛先の IP アドレスと TCP のポート番号で書かれると説明している[1]。

RFC 2979 は、パケットを調べるファイアウォールがすることを、そのまま通す、捨てる、自分で何らかの扱いをする、の三つに分けている[2]。判断の例には、内側のアドレスを送り元に名乗って外から来るパケットを止める、外から内への TELNET の接続を止める、メールやファイルを送ることを認めていない内側の機器から外への SMTP・FTP の接続を止める、などが挙がっている[2]。

ルールは、条件と結果の組で書く。「送り元が 192.168.1.0/24、プロトコルが TCP、宛先のポートが 22 なら通す」のような形だ。プロトコルは IP のヘッダーの番号で区別され、ICMP は 1、TCP は 6、UDP は 17、IPv6 の ICMP は 58 だ[3]。ポートは TCP と UDP にある番号で、ICMP にはポートがなく、種類（type）と符号（code）で区別する[4]。

この方式は、通信の中身までは見ない。中身で決めるには、アプリケーションの層で中継するプロキシを使う[1]。

状態を覚える方式は、行きの通信の戻りだけを通す

状態を覚えるファイアウォール（ステートフル）は、内側から始めた通信を表に記録し、その戻りのパケットを通す。NIST の用語集は、ステートフルインスペクションを、接続の状態も追いかけ、期待される状態から外れたパケットを止めるパケットフィルタとして定義している（出どころは NIST のファイアウォールの手引き SP 800-41 Rev. 1）[5]。状態を覚えないパケットフィルタで戻りを通すには、戻りに使われうるポートの範囲を、入ってくる側のルールで広く開けておくことになる。AWS の説明書は、仮想ネットワークの「ネットワーク ACL」が状態を覚えない方式で、入ってきた通信への応答にも出ていく側のルールが当てはまると書いている[6]。

Linux のファイアウォールの仕組み（netfilter）では、この記録を接続の追跡（conntrack）が受け持ち、パケットごとに状態を付ける。iptables の説明書によると、NEW は新しい接続を始めたか、まだ両方向のパケットを見ていない接続に属するパケット、ESTABLISHED は両方向のパケットを見た接続に属するパケット、RELATED は新しい接続だが既存の接続に関係するもの（FTP のデータの転送や ICMP のエラーなど）、INVALID はどの接続にも属さないパケットだ[7]。nftables では ct state established,related accept の1行で、行きの通信の戻りと、それに関係する ICMP のエラーを通せる[8]。

TCP は、SYN を送るところから三つのやりとりで接続を始める[9]。UDP には接続の始まりと終わりがないが、Linux の接続の追跡は UDP にも記録を作り、決まった時間がたつと消す。Linux カーネルの説明書では、確立した TCP の記録の既定の保持時間は432,000秒（5日）、UDP は30秒（やりとりが続いていると見なしたものは120秒）だ[10]。記録の数には上限（nf_conntrack_max）があり、いまの数は nf_conntrack_count で読める[10]。

ルールは上から読まれ、最初に合ったもので決まる製品が多い

確かめた範囲では、ルールを上から順に読み、最初に条件が合ったルールで決める作りが多いが、すべての製品がそうではない。

Linux の nftables では、チェーン（ルールの並び）の中のルールが順に評価される。説明書は、accept（通す）と drop（捨てる）を、評価をその場で終える結果だとしている[8]。drop はすぐに効き、そのあとのチェーンは評価されない。accept はそのチェーンでの評価を終えるだけで、同じ場所にあるあとのチェーンや、パケットの通り道のあとの段階で捨てられることはある[8]。ログを残す log や数を数える counter は評価を終えない文で、そのあとのルールに進む[8]。

AWS のネットワーク ACL は、ルールに付けた番号の小さい順に評価し、合ったルールがあれば、番号の大きいルールに逆のことが書かれていても、そのルールを当てる。一方、AWS のセキュリティグループは許可のルールしか持たず、すべてのルールを見てから通すかを決める[6]。ルールを読む前に、その製品の評価の決まりを確かめる。

最初に合ったもので決まる製品では、広い条件を上に置くと、その下の細かいルールに届かない。

順番の書き違いの例（上から評価し、最初に合ったもので決まる場合）
順番条件結果
1送り元 10.0.0.0/8、TCP の 22 番通す
2送り元 10.1.2.50、TCP の 22 番止める
3それ以外止める

2番で 10.1.2.50 からの接続を止めるつもりでも、10.1.2.50 は 10.0.0.0/8 に入るので、1番で通ってしまう。止めるルールを1番より上に置けば、意図どおりになる。nftables では、add はルールをチェーンの最後に足し、insert は先頭に足す[8]。最後に「全部止める」ルールを書いたチェーンへ add で許可を足すと、許可はその下に付き、合うパケットはその前に止められる。

既定で拒否し、必要なものだけを許す

ルールの基本は、通すものだけを書き、それ以外を全部止める「既定で拒否（default deny）」だ。NIST の SP 800-41 Rev. 1 は、ファイアウォールの方針で明示的に許していない入る通信と出る通信は、組織に必要ないものとして、一般に止めるべきだとしている[5]。MITRE ATT&CK も、ネットワークを分ける対策の一つとして、ネットワーク機器のアクセス制御リストで「既定で拒否」の方針を当てることを挙げている[11]。

既定が拒否になっているとは限らない。AWS のネットワーク ACL には、どの番号のルールにも合わないパケットを捨てる消せないルールが最後に付いているが、最初から用意される既定のネットワーク ACL は、すべての通信を通す設定になっている[6]。nftables のチェーンの既定の方針（policy）は accept で、drop にするには自分で書く[8]。ルールを全部消す nft flush ruleset のあとは、カーネルは正しい形のパケットをすべて受け入れる[8]。

「必要なもの」には、通信を支える ICMP のエラーが入る。RFC 2979 は、ファイアウォールを入れたことで、なければ動いていた正当な通信を壊してはならないとしている。例として、ICMP をまとめて止めると、経路の途中で一度に送れる大きさ（MTU）を調べる仕組みが働かなくなる問題を挙げ、DF ビットを立てた外向きのパケットを通すなら、その応答として返る「断片化が必要」のエラーを止めてはならない、とする。一方で、ping に使う Echo を止めるのは正当だとしている[2]。

IPv6 では、RFC 4890 が、通信を始めて続けるのに欠かせないものとして、Destination Unreachable、Packet Too Big、Time Exceeded（符号 0）、Parameter Problem（符号 1 と 2）を、止めてはならない ICMPv6 のエラーに挙げている[4]。IPv6 ではルーターがパケットを分けないので、Packet Too Big が届かないと、インターネットの一部に事実上届かなくなる、と同じ RFC は書いている[4]。

出ていく通信も止める

ルールは、外から入ってくる通信だけでなく、内から出ていく通信（egress）にも当てる。入る側だけを絞ると、内側の機器が乗っ取られたあと、その機器から外への通信はどこへでも通る。

MITRE ATT&CK は、通信を絞る対策（M1037）の中で、許していない外向きの通信を止めて、データの持ち出しと、攻撃者の指令サーバー（C2）との通信を防ぐことを挙げている[12]。RFC 2979 の例にも、メールやファイルを送ることを認めていない内側の機器から外への SMTP・FTP の接続を止めることが入っている[2]。

出ていく通信の送り元も確かめる。RFC 2827 は、送り元を偽ったパケットによるサービス妨害を減らすため、事業者が入口で偽の送り元を捨てることを求め、企業のネットワークの管理者も、自分のネットワークが偽った通信の出どころにならないようにフィルタを入れるべきだとしている[13]。組織に 203.0.113.0/24 が割り当てられているなら、外へ出ていくパケットのうち、送り元がその範囲の外にあるものは捨ててよい。

組織の中の通信も対象になる。MITRE ATT&CK のネットワークを分ける対策は、外と内のあいだ（南北）の通信だけでなく、内側どうし（東西）の通信もファイアウォールで絞ることを挙げている[11]。

許可の範囲は、必要な大きさで書く

許可のルールのアドレスの範囲は、必要な機器が入る最小の大きさで書く。IP アドレスの記事で見たとおり、プレフィックスが1ビット短くなるごとに範囲は倍になり、10.1.2.0/24 の256個を通すつもりで 10.1.0.0/16 と書けば、65,536個を通す。送り元を 0.0.0.0/0 と書けば、すべてのアドレスを許すことになる。

MITRE ATT&CK は、入ってくる通信を絞る例として、公開しているサーバーへの SSH（22番）と RDP（3389番）を、特定の IP アドレスの範囲からだけに限ることを挙げている[12]。ポートも、広く開けるほど、その範囲で待ち受けるほかのサービスに届く。

IPv4 と IPv6 は別々に書く。nftables の inet の表は IPv4 と IPv6 の両方を扱うが、ip saddr は IPv4 のヘッダーの送り元で、IPv6 の送り元は ip6 saddr で書く[8]。チェーンの方針が accept のまま、IPv4 のアドレスで止めるルールだけを書けば、IPv6 の通信はそのルールに当たらずに通る。AWS の既定のネットワーク ACL も、IPv6 の範囲を足すと、IPv6 用のルールが別に加わる[6]。

止めた記録をログに残し、SIEM に送る

ルールが意図どおりに働いているかと、だれがどこへつなごうとしたかは、ログを見ないと分からない。nftables では、ルールに log を書くと、合ったパケットの情報がカーネルのログに出て、dmesg か syslog で読める[8]。log は評価を終えない文なので、log prefix "nft-input-drop: " のように見分けるための前置きを付けて、止める直前に置ける。量が多いときは limit と組み合わせて、記録する件数を絞れる[8]。

ログの1行には、受けたインターフェース（IN=）、出すインターフェース（OUT=）、送り元（SRC=）、宛先（DST=）、プロトコル（PROTO=）、TCP と UDP なら送り元と宛先のポート（SPT=、DPT=）が並ぶ。Linux カーネルの書き出しの処理（nf_log_syslog）がこの形で書く[14]。どのアドレスからどのポートへ来たかが、ルールの条件と同じ項目で残る。

ログは1台の中に置いたままにせず、1か所に集めて、ほかの機器のログとつなげて読む。その仕組みが SIEM で、集め方はSIEM の記事に書いた。出ていく通信が止められた記録は、内側の機器が、決めていない相手とつながろうとした跡になる。

自分の環境で確かめる

試すのは、自分のパソコンか、自分で作った仮想マシンの中だけにする。遠くのサーバーで方針を drop に変えると、SSH の許可を書き忘れたときに自分も入れなくなるので、画面から操作できる仮想マシンが安全だ。

いまのルールは、管理者の権限で nft list ruleset を実行すると、人が読める形で出る。-a を付けると、ルールごとの番号（handle）も出る[8]。まず各チェーンの policy が accept か drop かを見て、上から順に条件と結果を読む。

新しいルールは、ファイルに書いて nft -c -f ファイル名 を実行すると、適用せずに書き方の誤りだけを調べられる[8]。僕は手元の nftables 1.0.9 で、次の6行を並べたファイルをこの方法で確かめた。inet の表に input のチェーンを方針 drop で作り、上から ct state established,related accept、ct state invalid drop、iif "lo" accept（自分自身への通信）、meta l4proto { icmp, ipv6-icmp } accept、ip saddr 192.168.1.0/24 tcp dport 22 counter accept、limit rate 5/minute log prefix "nft-input-drop: " を置いたものだ。最後の行まで来たパケットは、件数を絞ってログに残され、どれも方針で捨てられる。

ログは journalctl -k でカーネルのメッセージだけを出して読める[15]。前置きの文字で絞り込めば、止めた通信だけが並ぶ。counter を付けたルールは、nft list ruleset の出力に、合ったパケットの数とバイト数が出る[8]。数が増えないルールは、順番か条件が意図と違っている手がかりになる。接続の追跡の記録の数は、sysctl net.netfilter.nf_conntrack_count で読める[10]。

次に読む

  • /24 と /16 の違いは、許す相手の数で256倍になる。IP アドレスとプレフィックスの読み方

    /24 は先頭24ビットが同じ256個の範囲。1ビット短くなるごとに範囲は倍になる。プライベートアドレスなどの特別な範囲と、許可リストやログでの読み違いを、ルーティングの記事の続きとしてまとめた。

  • 開いているポートの数だけ、外からの入口がある。TCP と UDP とポートの読み方

    IP アドレスが機器を、ポート番号がその中のプログラムを指す。TCP は SYN・SYN-ACK・ACK で接続を作って順番と再送を受け持ち、UDP は接続を作らずに送る。開いているポートは入口になるので、不要なものは閉じ、スキャンと SYN フラッドの見え方を知っておく。
