# MOUTON — 「清潔感の科学」先行案内メール設計（BD-06）

**版**：v0.1　**作成**：2026-10-13　**状態**：配信サービスの本番接続・登録受付は**未実施**  
**関連**：[要件定義](../REQUIREMENTS.md)、[基本設計](../DESIGN.md)、[発売前LP](cleanliness-prelaunch.md)、[個人情報保護ページ](../src/privacy.njk)

## 1. この機能の目的・制約

完成済み・発売準備中の「清潔感の科学」（A4・75ページ、税込2,980円）の**発売・販売開始に関する案内だけ**を、本人が事前に申し込んだ場合にメールで届ける。

- 登録は**無料**。商品の注文・予約・支払い・購入義務は発生しない。
- 初期段階で集めるものは**メールアドレスのみ**。氏名、電話番号、健康情報、自由記述、SNS IDは求めない。
- 既存の5ページ無料Web/PDFサンプルは登録なしで読める。登録しない人に閲覧制限を設けない。
- 本件の同意を通常のメールマガジンや他の商品広告へ転用しない。配信範囲を拡大するなら同意を見直す。
- メール・同意履歴は接続した配信サービスで管理し、GitHubの公開リポジトリやGA4に登録者情報を保存しない。
- **受付開始は別のオーナー判断**。この基本設計だけでは登録を有効化しない。

## 2. 配信サービス候補（2026-10-13時点の公式機能を照合）

| 候補 | 公式情報に基づく長所 | 要検証・考慮事項 | 初期方針 |
| --- | --- | --- | --- |
| **Buttondown** | 静的サイトが使う通常のHTML POST用 `embed-subscribe` 送信先を提供。原則ダブルオプトインを要求 | 送信元ドメイン確認、同意と解除の履歴、日英のメール文面、配信上限と料金、データ処理場所を実アカウントで確認する | **第一候補**。このリポジトリの暫定フォームはButtondownの公開HTML方式だけを受け付ける |
| **MailerLite** | 埋め込みフォーム・共有URL・ダブルオプトイン・同意チェック欄などを提供 | 一般的な埋め込みはサービス側が生成するJS/HTMLを設置する方式。フォーム仕様に合わせて実装する別PRが必要 | 代替候補 |
| **Brevo** | 埋め込みフォーム、同意関連フィールド、ダブルオプトイン、配信停止管理を提供 | 外部で作成したフォームは二段階確認の自動化設定が必要な場合がある。サービス固有の連携と確認が必要 | 代替候補 |

## 3. 画面・情報・登録フロー

```text
LP：cleanliness-science.html#notify
  │
  ├─ 設定未確認 →「先行案内の受付は準備中」＋無料サンプルへ（現状）
  │
  └─ 事前チェック完了 → メールアドレス入力＋同意チェック
                         │
                         ▼
                 ButtondownのHTTPSフォームPOST
                         │
                         ▼
                 確認メールが届く（未確定／unactivated）
                         │
                         ▼
                 本人が確認リンクを押す
                         │
                         ▼
                 Buttondown側で有効登録を確認
                         │
                         ▼
                 発売・販売開始の案内のみ送信
                         │
                         └─ メールの配信停止リンクからいつでも解除
```

**送信試行は登録成功ではない**。`waitlist_submit`はフォーム送信の試行のみを測る。初期の「有効登録数」はButtondown等のプロバイダーが報告する**確認済み購読者件数**を正とする。フォーム送信後すぐにサイト側で`generate_lead`や`purchase`を発火させない。

### フォームに必要な表示

- 明確なタイトル：「発売したら、お知らせします」
- 必須メール入力、**デフォルトOFFの必須同意チェック**：「『清潔感の科学』の発売・販売開始に関するメール案内を受け取ることに同意します（無料・購入義務なし）。」
- プライバシーポリシーへのリンク、登録後はメールに届く確認リンクで確定する説明、配信停止可能の説明。
- 送信先は実在するButtondownのHTTPS URLのみ。**架空のフォーム、フォーム送信だけでの「登録完了」表示は不可**。
- 初期実装のフォームは `name="embed" value="1"` を含むHTML POST。追加メタデータや確認画面の挙動はプロバイダーの実画面で検証する。

## 4. 法令・プライバシーの考え方

日本で送る広告・宣伝目的のメールについては、**特定電子メール法**により原則事前の同意、同意を示す記録の保存、送信者情報の表示、受信拒否への対応などが求められる。内容が商品販売を目的とするため、発売案内メールも広告・宣伝メールに該当する前提で運用する。適用範囲と表示詳細は最終的に事業者として確認する。単に登録欄のチェックボックスがあるだけで法令対応を保証しない。

**公開前の運用者チェック**：
1. サイトとメールの送信責任者名・連絡方法・必要な表示を確定する（公開の運営者情報・プライバシーとの整合）。
2. 日本語の同意文と送信目的、配信頻度の目安（「発売・販売開始に関する数通のみ」など実際の計画）を明示する。
3. Double opt-inが実際に届き、**未確認アドレスに案内が送られない**ことを確認する。サービス側で同意の日時・取得経路・確認状況・同意文の版を保存・説明できるか確認する。必要に応じて法定の保存期間を調査する。
4. 実際にメールを送り、送信者表示・問い合わせ導線・**解除リンク**を確認し、解除後に再送しないことを試す。
5. サービスの個人データ処理、保存地域、委託先、保持・削除・輸出、本人からの開示・削除要求への対応を確認し、サイトのプライバシー文面をサービス名付きで更新する。
6. 配信の対象を本商品の発売案内に限定し、会員登録・販促の別目的へ同意なく転用しない。
7. 配信先アカウントの二要素認証・ドメイン認証（SPF/DKIM/DMARC等の必要な設定）・管理権限も確認する。
8. 設定の証拠を**非公開**の運用記録に残し、メールアドレスや同意ログをGitHub Issue/PRへ貼らない。

公的資料：[消費者庁等「特定電子メール法のポイント」](https://www.caa.go.jp/policies/policy/consumer_transaction/specifed_email/pdf/specifed_email_180709_0001.pdf)／[e-Gov 法令検索](https://laws.e-gov.go.jp/law/414AC0100000026)

## 5. 実装済みの安全ゲート（**受付OFFのまま**）

`src/_data/site.js` の `prelaunch` に以下を設定している。

| 項目 | 既定値 | 目的 |
| --- | --- | --- |
| `enabled` | `false` | **明示的な受付スイッチ** |
| `provider` / `waitlistService` | 空欄 | Buttondownに限るホストと表示名の一致確認 |
| `waitlistAction` | 空欄 | 実アカウントの公式HTML POST送信先 |
| `waitlistEmailField` | `email` | サービスが期待するメール入力名 |
| `doubleOptInVerified` | `false` | 実際の確認メール・確定登録を検証済み |
| `unsubscribeVerified` | `false` | 実際の配信停止を検証済み |
| `privacyReviewed` | `false` | 個人情報の利用・委託先と公開文を照合済み |
| `senderDetailsVerified` | `false` | 送信責任者・解除・問い合わせ等の送信者表示を確認済み |
| `ready` | 自動算出 `false` | 全条件を満たす場合のみフォームを公開 |

- `scripts/waitlist-readiness.mjs` が有効化設定を検証する。**enabled=falseならURLを設定してもフォームは出ない。**
- `enabled=true`で条件を満たさない場合はEleventyビルド（＝CI）を**失敗**させる。許可ドメインとパスはButtondownのHTML埋め込み送信先だけ。異なるサービスでは無理にURLを差し替えず、別Issueで実装する。
- LPテンプレート、プライバシー文面、CSPのフォーム送信先は同じ`ready`を判定する。
- `npm run test:waitlist` が構成変更・不正なURL・レビュー未実施・既定の受付OFFを自動テスト。
- 一連のフラグは**自己申告する運用チェック**であり、trueにするだけで実サービスの安全性を保証するものではない。ログに根拠を残してオーナーが承認するまでfalseを維持する。

## 6. 本番有効化は別Issue／PRで行う

1. サービスを選定し、**オーナー自身のアカウント**と送信者認証を設定。自動で登録完了したふりをしない。
2. 本番フォームのaction（Buttondownの場合は`https://buttondown.com/api/emails/embed-subscribe/<実際のユーザー名>`）を**非個人情報**として確認。APIキーは絶対に公開せず、HTMLフォーム送信先だけを使う。
3. 同意文、プライバシー、配信目的、解除手順、連絡先をレビュー。実テスト用アドレスで **未確認→本人確認→登録→案内送付→配信停止** の全工程をテストし、プロバイダーの記録を非公開で残す。
4. すべてが検証できた後に`site.prelaunch.enabled=true`、`provider='buttondown'`、`waitlistService='Buttondown'`、正しい`waitlistAction`と4つの検証フラグを設定。**この変更自体が公開開始なので、レビューしてからマージ**。
5. `npm ci && npm test`／ブラウザでフォームのラベル、必須チェック、送信、確認画面、同意未チェックの拒否、プライバシー表示を検証。実メールアドレスをテストログへ残さない。
6. 本番へ公開後、管理画面で1件の確認済みテスト登録・解除を再確認。送信結果・プロバイダー側の実際の有効登録だけをKPIに使う。
7. 配信サービスに障害がある、または同意・プライバシー条件を満たさなくなった場合は`enabled=false`に戻してPR・公開する。既存のメールリストの取扱いはサービス管理画面で対応する。

**現時点で未完了**：Buttondown等の実契約・エンドポイント・同意履歴・解除確認・法務確認・初回の実登録。公開サイトでは従来どおり「先行案内の受付は準備中」と無料サンプルを表示する。
