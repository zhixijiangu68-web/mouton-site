# SaaS をやるなら何を、どの順で（2026-10-17、AI の提案）

**位置づけ**：オーナーの「SaaS をしたい」（2026-10-17）を受けた AI の提案。**決定ではない**。採用するなら、この文書の「決めてほしいこと」に答えたうえで `CLAUDE.md` と `docs/product-first-strategy-20261015.md` に反映する。
**前提にした資料**：`BRAND.md`「点と線」、`docs/product-first-strategy-20261015.md`、`docs/project-charter.md`、`docs/philosophy-sales-20261016.md`、`promo/status.md`、リポジトリ `KIOKU`。

## 1. 結論（提案）

**MOUTON の SaaS は「点と線」の道具にする。** 点（今日の一つの行動）→ 線（試したことを書き残す）→ また点、のサイクルを回すための、小さなウェブアプリ。

- `BRAND.md`「点と線」に「**このサイクルを回す道具をつくる**」と書いてある。SaaS はその道具を、人に使ってもらい、お金をいただく形にしたもの。新しい事業ではなく、いまの方針の続き。
- 有料記事3本（キルケゴール・ニーチェ・スピノザ）は「最初の点を打つまで」を担い、道具は「打ったあと、線にして、また点を打つ」を担う。**記事が入口、道具が続き**、という一本の流れになる。
- 最初は **無料・ログインなし・端末に保存**（KIOKU と同じ、HTML 1枚＋localStorage）。有料化（＝SaaS）は、使い続ける人が実際にいると分かってから。

## 2. いまの方針とのつじつま

正直に書くと、いますぐ SaaS を始めるのは、2つの点でいまの方針とぶつかる。

| ぶつかるところ | どう折り合いをつけるか |
|---|---|
| 「商品の完成 → 決済・納品 → 集客 → 実購入」の順を守る。売上0件で、Stripe・Worker・R2・特商法がオーナー側で止まっている | 道具の**無料版**は決済と無関係なので、止まっている作業を待たずに AI が作れる。**有料化はしない**まま置く。3本の販売準備が先に進むのを妨げない |
| 「新しい有料商品はまだ作らない」（2026-10-16、オーナー選択）／案件定義で「会員登録・会員DB・独自決済」は未確定 | 無料版は有料商品でも会員制でもない。段階2以降（口座・同期・月額）に進むときに、改めてオーナーが決める |

もう一つの注意。SaaS は「作って終わり」にならない（口座・支払い・解約・問い合わせが毎月続く）。一人＋AI で回せる大きさに、意図して小さく保つ。

## 3. 候補の比較

| 候補 | 中身 | 良い点 | 弱い点 | 判定 |
|---|---|---|---|---|
| **A. 点と線の道具** | 今日の一つの行動を決め、やったことを書き残し、つながりを見て、次を決める | 方針そのもの。記事 → 道具の流れが一本になる。ブランドの世界観で作れる | 「習慣アプリ」はすでに多い。差は「問いを置く・答えを渡さない」という設計にしかない | **第一候補** |
| B. KIOKU（アニメの記録アプリ） | 観たアニメを記憶に残す。HTML 1枚、localStorage、外部 API（tenrai、RSS）から取得 | すでに動く形がある。アニメは市場が大きい | MOUTON と無関係で、ブランドが二つに割れる。外部 API 頼みで、有料にすると止まったときの責任が重い | 別事業として扱う。いまは触らない |
| C. まったく新しい SaaS（業務向けなど） | 未定 | 単価が高い市場もある | 顧客も強みもゼロから。10月の「最初の1件」からいちばん遠い | 今回は取らない |

A を取る理由は、**いちばん小さく出して確かめられる**から。B・C は、オーナーが「MOUTON とは別に」と決めたときに改めて考える。

## 4. 最小の形（入れるもの・入れないもの）

**入れるもの**（これだけで一周回る）

1. **点**：「今日、試す一つ」を1行だけ書く（例文は置かない。何を試すかは本人が決める）
2. **線**：その日の終わりに「やってみて、どうだったか」を数行。やらなかった日も、そのまま書ける（責めない）
3. **つながり**：過去の点と線を、日付順に一覧で見る。並べて読むと自分のくせが見える、以上のことはしない
4. **また点**：最後に問いが一つだけ出る（「見えたことから、次に試す一つは？」）。答えは本人が書く
5. **持ち出し**：書いたものを自分の手元に残せる（テキストで書き出し）。端末に閉じ込めない

**入れないもの**（`BRAND.md`「安易に与えない」と合わないため）

- 穴埋め（＿＿＿）、テンプレート、おすすめの行動
- 達成率・連続日数・バッジ・リマインド通知などの、続けさせるための演出
- AI による助言・採点
- SNS 共有、ランキング

## 5. 段階と、各段で確かめること

| 段階 | 作るもの | 確かめること（これが出るまで次に進まない） |
|---|---|---|
| **0. 自分で回す** | HTML 1枚の試作。ムートン自身が2週間使う | 自分が使い続けられるか。使わなくなったなら、その理由 |
| **1. サイトに置く（無料）** | トップ「点と線の回し方」から入れる無料の道具。記事3本の最後の問いから続けて使える | 第三者が使うか（開いた人数ではなく、**2回目以降に書いた人数**） |
| **2. 口座と同期** | メールの magic link でログイン。Worker ＋ D1 に保存。端末をまたいで使える | 口座を作ってまで使いたい人がいるか |
| **3. 有料（ここから SaaS）** | Stripe の定期課金。価格は仮説を一つ決めて実決済で確かめる | **知人ではない第三者の月額の実決済1件**（記事3本と同じ基準） |

段階2・3に進むかは、そのつどオーナーが決める。段階1までは AI が進められる。

## 6. 技術（いまある資産を使う）

- **段階0〜1**：Eleventy のサイトに 1ページ追加（`src/tenten.njk` のような形。名前は未定）。JS と localStorage だけ。KIOKU の作り方を流用できる。デザインはサイトの `site.css` に合わせ、独自の固定幅を増やさない
- **段階2**：`fulfillment-worker/`（Cloudflare Worker ＋ D1 ＋ Resend）を土台にする。magic link のメール送信は Resend、保存は D1。新しい基盤は増やさない
- **段階3**：Stripe Billing（定期課金）。Payment Link は使えるが、解約ページ（Customer Portal）が必要
- 公開リポジトリに秘密鍵・個人データを入れない（いまのルールと同じ）

## 7. SaaS にすると増える義務（段階3の前に）

- **特定商取引法に基づく表記**に、定期課金の条件（金額・周期・解約の方法と期限）を足す。すでに準備中の `src/_data/legal.js` に項目を加える
- **利用規約**（新規）と**プライバシーポリシー**の更新（日記に近い内容を預かるので、保管・削除・閲覧しないことを明記）
- **解約**を、問い合わせなしで本人が自分でできるようにする（Stripe の Customer Portal）
- 消費税（内税表示）、インボイスの要否、領収書の出し方
- 問い合わせの窓口（いまは X だけ。メールが要る）

## 8. 決めてほしいこと（オーナー）

1. **SaaS ＝「点と線」の道具、でよいか。** 違うもの（KIOKU、別の事業）を考えているなら、その一言がほしい
2. **順番**：記事3本の販売準備（Worker → Stripe → R2 → 特商法）と並行してよいか、販売が始まるまで待つか。AI の提案は「無料版だけ並行、有料化は販売後」
3. **段階1の置き場所**：トップの「点と線の回し方」から入れる無料の道具として出してよいか（トップの構成を少し変える）

## 9. 決まったら AI がやること

- 段階0の試作を1ページで作り、`npm run build` → `npm test` を通す（1回の仕事）
- オーナーが2週間使ったあとの感想を聞いて、段階1に出すか決める
- 段階2以降の設計（magic link、D1 の表、Stripe Billing）は、段階1で「2回目以降に書いた人」が出てから書く
