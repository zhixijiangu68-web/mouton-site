## 1. アーキテクチャ

| 層 | 主な配置 | 責務 |
| --- | --- | --- |
| Eleventy入力 | [src/](../../src/) | Nunjucks／HTMLテンプレート、記事、データ |
| ビルド設定 | [eleventy.config.js](../../eleventy.config.js) | フィルタ、ショートコード、生成処理 |
| サイト設定 | [src/_data/site.js](../../src/_data/site.js) | サイトURL、GA4、商品表示、フォーム・決済ガード |
| 生成HTML | リポジトリ直下、[en/](../../en/) | 公開サイトに配信される成果物。直接編集しない |
| 画像・静的ファイル | [images/](../../images/)、CSS/JS | 表示素材 |
| 回帰チェック | [tests/](../../tests/)、[scripts/check-site.mjs](../../scripts/check-site.mjs) | 動作と静的品質の検証 |
| CI | [.github/workflows/](../../.github/workflows/) | Build、Browser smoke、Security scan等 |
| 商品納品バックエンド | [fulfillment-worker/](../../fulfillment-worker/) | Stripe署名検証、注文照合、非公開R2、メール配布（コードあり、未デプロイ） |

静的Webのページ配信と、Stripe/Cloudflare/Resendによる非公開PDF納品を同じものと考えない。

## 2. ローカル操作（既存npmスクリプト）

    npm ci
    npm run build
    npm test
    npm start

- npm run build：Eleventyで生成HTMLを同期。
- npm test：デザイン、キャンペーンURL、先行案内の各単体テスト、Eleventyのビルド、サイトリンク等のチェック。
- npm start：ローカルプレビュー。
- Browser smokeは専用ワークフローが実行するため、npm testだけでSafariや全ブラウザを保証しない。
- Worker側は別のpackage.json／テストと環境準備を持つ。サイトのテスト成功だけで納品が完成したとは言えない。

## 3. 設定と秘密情報の境界

| 種類 | 管理場所 | 禁止行為 |
| --- | --- | --- |
| 公開可能な表示設定 | src/_data/site.js | 未検証の本番URLを公開する |
| Stripe本番秘密鍵／Webhook署名鍵 | Cloudflare Secrets等 | GitHubへコミット、IssueやPRに貼付 |
| メール送信鍵／署名鍵 | Cloudflare Secrets等 | クライアントJSに置く |
| 有料PDF原本 | 非公開R2など | 公開GitHubや公開URLへアップロード |
| 注文・購入者情報 | D1／Stripe等の管理基盤 | ログや公開資料へ生データを記載 |
| テスト用設定 | テスト専用の環境 | 本番のキー・価格IDと混在させる |

## 4. 7つの品質ゲート

| 段階 | 主な検査 | 現状の管理箇所 |
| --- | --- | --- |
| 1 | 要件・受け入れ条件が明記されている | PRテンプレート |
| 2 | Node／Eleventyの自動テスト | npm test |
| 3 | ブラウザで操作して確認 | tests/browser-smoke.mjs |
| 4 | CIで繰り返し実行 | build-check.yml、browser-smoke.yml |
| 5 | 依存関係／コードの安全性 | security-scan.yml、Dependabot |
| 6 | 失敗をIssueに記録して切り分け | ci-failure-triage.yml |
| 7 | レビュー／必須チェック後のマージ | GitHub Ruleset（管理画面での有効化を別途確認） |

## 5. 実装時チェックリスト

- [ ] Issueにユーザー価値・現状・受け入れ条件・非対象を書いた
- [ ] ソースと生成HTMLの整合を保ち、生成HTMLを直接編集していない
- [ ] 日本語と英語のリンク、相対パス、見出しを点検した
- [ ] PCとモバイルで新旧の動作を比較した
- [ ] npm run build／npm testのログを保存した
- [ ] PRのBuild check／Browser smoke／Security scanを確認した
- [ ] データの機密性、個人情報、著作権、画像ライセンスを点検した
- [ ] モバイルSafariを要する変更は実機で確認した
- [ ] 失敗した必須CIを無視してマージしない
- [ ] 本番反映後の監視・ロールバック手段を整理した

## 6. 回帰テスト設計

| ID | ユーザー視点のテスト | 失敗例 |
| --- | --- | --- |
| QA-01 | トップの3カードからテーマ一覧へ進める | クリック不能／404 |
| QA-02 | Night/Day切替が保存される | リロードで崩れる |
| QA-03 | journal.htmlで記事検索・絞り込み | 結果が出ない |
| QA-04 | モバイルメニューの全リンクが動く | 開くが反応しない |
| QA-05 | 旧 #journal から記事一覧へ移動する | 旧リンク利用者が迷う |
| QA-06 | LPと無料サンプルを行き来できる | PDFリンク404 |
| QA-07 | 販売準備中は本番購入CTAを表示しない | テストリンク・購入可能表示 |
| QA-08 | Workerが未払い・重複・改ざん・期限切れを拒否 | 不正な納品や二重配信 |
| QA-09 | 有料PDFを公開アセットに含めない | 未購入でも入手可能 |

## 7. 障害時の基本手順

1. 事象、UTC/JST日時、URL、影響範囲、直前のPRを記録。
2. 重大な決済・個人情報リスクなら購入受付を停止する判断を最優先する。
3. GitHub Actions、必要ならWorkerログやStripe管理画面を権限者が確認。公開Issueに個人情報を貼らない。
4. 最小限の修正または安全な以前の状態へ戻すPRを作る。
5. 再現と解消、影響した顧客への対応を記録する。

**この資料自体はコード・デプロイ・E2Eテストを実行していない。**
