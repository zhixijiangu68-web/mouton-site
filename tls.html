守る

経路を乗っ取っても、本物の鍵がなければ本物にはなれない。TLS が守る三つのこと

暗号化・完全性・相手の確認、TLS 1.3 のハンドシェイク、証明書と認証局、名前の確認、Certificate Transparency、守る側の設定を、RFC と公式の文書で確かめた

約12分更新日 2026年11月7日

TLS は、通信の中身を暗号にし（暗号化）、途中での書き換えに気づき（完全性）、つないだ相手が名乗ったとおりの相手かを証明書で確かめる（相手の確認）。ルーティングの記事に書いた経路の乗っ取りで通信が別の場所へ流れても、この三つが働いていれば、流れた先で中身は読まれず、偽のサーバーを本物と取り違えない。この記事は、TLS 1.3 の流れ、証明書と認証局、名前の確認、Certificate Transparency、守る側の設定を、RFC と公式の文書で確かめたものだ。例の名前は、文書のために取ってある example.com と example.net だけを使う[1]。

TLS は、暗号化・完全性・相手の確認を受け持つ

TLS 1.3 の決まり（RFC 8446）は、TLS の目的を、通信する二者のあいだに安全な通り道を作ることとし、その性質を三つ挙げている[2]。相手の確認（サーバーは毎回、クライアントは必要なときだけ確かめる）、暗号化（送ったデータは両端にしか見えない）、完全性（気づかれずに書き換えることはできない）だ。

RFC 8446 は、これらがネットワークを完全に握った攻撃者に対しても成り立つべきだとしている[2]。経路を乗っ取った側にパケットが届いても、中身は暗号のままで、書き換えれば受け取った側が気づく。本物のサーバーになりすますには、本物の秘密鍵が要る。

隠さないものもある。RFC 8446 は、TLS は送るデータの長さを隠さないと書いている[2]。IP アドレスも、ルーターが読んで次の行き先を決めるので暗号にできない。TLS が守るのは、どこと通信しているかではなく、何をやりとりしているかと、相手が本物かだ。

TLS 1.3 は、鍵を決めてから相手を確かめる

TLS 1.3 の最初のやりとり（ハンドシェイク）は、鍵の交換、サーバーの設定、相手の確認の三つの段に分かれる。RFC 8446 は、鍵の交換の段よりあとのものは、すべて暗号にして送る、としている[2]。

TLS 1.3 のハンドシェイクの主なメッセージ（証明書でサーバーを確かめるとき）
メッセージ送る側役目暗号にするか
ClientHelloクライアント使える版と暗号の候補、鍵の片割れ（key_share）、つなぎたい名前（server_name）を送るしない
ServerHelloサーバー選んだ暗号と、サーバーの鍵の片割れを返す。ここで共通の鍵が決まるしない
EncryptedExtensionsサーバー暗号の選択に関わらない、そのほかの取り決めを返すする
Certificateサーバーサーバーの証明書（と途中の認証局の証明書）を送るする
CertificateVerifyサーバーここまでのやりとり全体に、証明書の公開鍵と対になる秘密鍵で署名するする
Finished両方やりとり全体の MAC（改ざんを見つけるための値）で、同じ鍵を持っていることを確かめ合うする

鍵の交換は、ディフィー・ヘルマン鍵交換（楕円曲線を使うものを含む）で行う。両者が一回きりの鍵の片割れを送り合い、それぞれ手元で同じ秘密を計算するので、秘密そのものは通信路を流れない[2]。

相手の確認は、CertificateVerify が要になる。証明書は公開されているので、偽のサーバーでも本物の証明書を送ることはできる。しかし、そのやりとりに合った署名は、対になる秘密鍵がなければ作れない[2]。途中でメッセージを差し替えれば、Finished の MAC が合わなくなる。

RFC 8446 は、TLS 1.2 との違いとして、固定の RSA による鍵の交換を外し、公開鍵による鍵の交換はすべて前方秘匿性を持つようになったと書いている。あとでサーバーの秘密鍵が漏れても、通信の鍵を消してあれば、過去の通信は解けないという性質だ[2]。

ClientHello は鍵が決まる前に送るので暗号にならず、中の server_name（SNI）の名前も見える。サーバーはこの名前で、出す証明書を選ぶ[2]。

証明書は、名前と公開鍵の組に認証局が署名したもの

証明書は、「この名前の持ち主の公開鍵はこれだ」という組に、認証局（CA）が署名したものだ。インターネットでの証明書の決まり（RFC 5280）は、証明書の検証の主な目的を、証明書に書かれた名前と公開鍵の結び付きを確かめることだとしている[3]。

使う側は限られた数の CA の公開鍵しか最初から持っていないので、サーバーの証明書から、途中の CA（中間 CA）の証明書をたどって、手持ちの CA までつなげる。RFC 5280 は、この並びを証明書のパス（チェーン）と呼ぶ[3]。起点の CA（トラストアンカー）は、通信とは別の信頼できる手段で渡されたものとされ、ブラウザーや OS が持つ CA の一覧がこれにあたる[3]。

RFC 5280 の検証の手順では、チェーンの一枚ごとに、少なくとも次を確かめる[3]。一枚前の CA の公開鍵で署名が検証できること。今の時刻が有効期限の中にあること。今の時刻に取り消されていないこと。発行者の名前が、一枚前の証明書の持ち主の名前と合うこと。どれか一つでも欠ければ、チェーンは通らない。

RFC 8446 は、細かい検証は RFC 5280 に任せたうえで、MD5 を使う署名の証明書ではハンドシェイクを止めなければならないとし、SHA-1 も止めることを勧めている[2]。

名前の確認で、別のサイトの証明書を見分ける

チェーンが検証できても、それだけでは足りない。攻撃者は、自分で正しく取った example.net の証明書を、www.example.com として出せるからだ。そこで、証明書の名前が、つなごうとした名前と合うかを確かめる。

この決まりは RFC 9525（2023年、RFC 6125 を置き換えた）にある。クライアントは、利用者が入力した URL などから、サーバーの出した名前とは別に「つなぎたい名前」を作り、証明書の Subject Alternative Name（SAN）の欄の DNS の名前と比べる。Common Name の欄で名前を表すことは、RFC 9525 ではもう正しくない[4]。RFC 5280 は、CA が SAN のすべての部分を確かめなければならないとしている[3]。

名前は、ドットで区切ったラベルごとに、大文字と小文字を区別せずに比べる。* を使ったワイルドカードの証明書には決まりがある。* は一つだけで、いちばん左のラベル全体でなければならず、合うのは一つのラベルだけだ[4]。*.example.com の証明書は www.example.com には合うが、example.com にも a.www.example.com にも合わない。

名前が合わなければ、RFC 9525 は、自動で動くプログラムは接続を止めて記録を残すべきで、この確認を標準で切ってはならないとしている。人が使うソフトも、食い違いを知らせて接続を止めるべきだとしている[4]。

証明書には期限があり、途中で取り消すこともある

証明書には有効期限があり、期限が切れた証明書はチェーンの検証を通らない。RFC 5280 では、期限は notBefore（いつから）と notAfter（いつまで）の二つの日時で表し、両端の日時も期限に含む[3]。

公開の Web で使う証明書の期限の上限は、CA とブラウザーの作る CA/Browser Forum の基本要件（Baseline Requirements）が決めている。いまの版では、2026年3月15日より前に発行したものは398日まで、2026年3月15日からは200日まで、2027年3月15日からは100日まで、2029年3月15日からは47日までだ[5]。期限が短くなるほど、更新を手でするのは難しくなる。ACME（RFC 8555）は、ドメインを持っていることの確認と証明書の発行を、CA と申請する側とのあいだで自動でするための決まりだ[6]。

期限の前でも、秘密鍵が漏れたときなどは、証明書を取り消す（失効させる）[3]。取り消した証明書は、CA が定期的に出す署名付きの一覧（CRL）に通し番号で載る。RFC 5280 は、一覧が1日ごとなら取り消しが届くのも最大でそのぶん遅れる、という限りも書いている[3]。問い合わせに応じて状態を返す OCSP もあるが、基本要件は2023年の改定で OCSP を任意にし、CRL を必須にした[5]。

Certificate Transparency は、発行された証明書を公開の記録に残す

Certificate Transparency（CT）は、発行された証明書を公開の追記だけの記録（ログ）に残し、不正な発行をあとから見つけられるようにする仕組みだ。信頼される CA はたくさんあり、技術的にはどの CA でもどの名前の証明書でも発行できてしまう。CT はその発行を止めるのではなく、見える場所に出す。

CT の最初の決まりは RFC 6962（2013年）で、版2が RFC 9162（2021年）だ。どちらも実験的な（Experimental）RFC として出ている[7][8]。RFC 9162 によると、ログは証明書のチェーンを受け付けると、署名付きのタイムスタンプ（SCT）を返す。TLS のクライアントは、受け入れる証明書に SCT が付いていることを求めることができる。ログが追記だけであることは、マークル木というハッシュの木で確かめられる[8]。

RFC 9162 は、ログそのものは不正な発行を見つけないと書いている。見つけるのはドメインの持ち主などで、ログを見張り（モニター）、思いがけない証明書が出ていれば、CA に取り消しを頼むなどする[8]。

ブラウザーの側も CT を求めている。Chrome の CT の方針は、CT を求める版の Chrome では、公開の Web で信頼される TLS の証明書は、方針を満たす SCT が付いていなければ検証を通らない、としている[9]。2015年には、Google が、自社が頼んでいない google.com の証明書（発行前の形のもの）が Symantec の CA から出ていたことを、CT のログで見つけたと報告している[10]。

守る側は、古い版を止め、警告を無視せず、発行を見張る

守る側がすることは、古い版を使わない、証明書の警告で止まる、自分のドメインの発行を見張る、発行できる CA をしぼる、の四つだ。

TLS 1.0 と 1.1 は、RFC 8996（2021年）で廃止された。RFC 8996 は、どちらも使ってはならず、どの版からもこの二つへ交渉で下げてはならない、としている。理由の一つは、ハンドシェイクの完全性が SHA-1 に頼っていることで、2の77乗回ほどの計算ができる攻撃者は、ハンドシェイクを古い版へ下げさせられる、と書いている[11]。TLS の使い方の勧め（RFC 9325、BCP 195）は、TLS 1.2 は対応しなければならず、TLS 1.3 には対応すべきで、対応するなら 1.3 を優先して選ばなければならない、としている[12]。

証明書の警告は、名前・期限・チェーンのどれかが通らなかったという知らせで、先へ進めると相手の確認がなくなる[4]。OpenSSL の説明書も、どんな証明書でも受け入れるのは試験の道具だからで、ふつうのプログラムがそうすると中間者攻撃に弱くなると書いている[13]。

自分のドメインは、CT のログを見張れば、身に覚えのない発行に気づける[8]。

発行できる CA は、DNS の CAA レコード（RFC 8659）でしぼれる。CAA は、そのドメインの証明書を発行してよい CA を、ドメインの持ち主が DNS に書いておくものだ[14]。たとえば example.com. CAA 0 issue "ca1.example.net" と書けば、ca1.example.net 以外の CA には発行しないよう求めることになる。issue ";" はどの CA にも発行させない書き方で、ワイルドカードの証明書は issuewild で別に決められる[14]。基本要件は、CA に発行の手続きの中で CAA を調べることを求めている[5]。ただし CAA は CA が発行する前に確かめるもので、RFC 8659 は、接続する側が証明書の検証に CAA を使ってはならない、としている[14]。発行の前は CAA で、発行のあとは CT で見る、という組み合わせになる。

自分の環境で確かめる

TLS の観察は、自分のパソコンの中だけでできる。他人のサーバーに試験の接続をしたり設定を探ったりはせず、自分で立てたサーバーと、許可された演習の環境だけで試す。

まず openssl req などで、自分だけの CA と、SAN に www.example.com を入れたサーバーの証明書を作る。それを試験用のサーバー openssl s_server に渡し、-accept 127.0.0.1:8443 で自分のパソコンの中だけで動かす[15]。

つなぐ側は openssl s_client だ。-connect 127.0.0.1:8443 でつなぎ、-servername www.example.com で ClientHello の SNI を決める[13]。-CAfile に自分の CA の証明書を、-verify_hostname www.example.com で確かめる名前を渡す[16]。-verify_return_error を付けると、検証の誤りでハンドシェイクを止める。付けないと、s_client は誤りを表示したうえで接続を続ける[13]。

手元の OpenSSL 3.0 では、正しい名前と CA で、版 TLSv1.3、検証 OK と表示された。確かめる名前を www.example.net に変えると「hostname mismatch」で、-CAfile を外すと「unable to get local issuer certificate」で止まった。名前の確認とチェーンの検証が、別々に働いている。

s_client の出力を openssl x509 -noout -subject -issuer -dates -ext subjectAltName に渡すと、持ち主・発行者・期限・SAN を表示できる。-checkend に秒数を渡すと、そのうちに期限が切れるかを終了コードで返すので、期限切れの見張りに使える[17]。なお -showcerts が表示するのは、サーバーが送った証明書の並びで、検証したチェーンではない[13]。

古い版を断るかは、自分のサーバーに -tls1_1 を付けてつなげば確かめられる[13]。手元の OpenSSL が古い版を使わない設定なら、「no protocols available」と送る前に止まる。
