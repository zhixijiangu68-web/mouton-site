Linux のログは、手元にあるかぎり消せる。だから外へも送っておく

syslog の facility と severity、rsyslog と journald、auth.log と secure、sshd と sudo の行、last と lastb、auditd、logrotate、別の機械への転送を、RFC とソフトの公式文書で確かめた

約12分更新日 2026年11月13日

Linux のログは、多くのプログラムが syslog の形で出し、rsyslog がテキストのファイルに、systemd-journald が journal という独自の形のファイルに書く。ログインや権限の記録は、sshd と sudo の行、wtmp と btmp、auditd の記録に分かれて残り、その機械の管理者の権限があれば消せるので、別の機械にも送っておく。SIEM の検知ルールの記事の SSH の総当たりは、この記事の sshd の行を数えている。Windows の側は Windows のイベントログの記事に書いた。例のアドレスは文書用のもの（203.0.113.0/24・198.51.100.0/24）、ユーザー名は架空のものだけを使う。

syslog のメッセージは、facility と severity を持つ

syslog のメッセージには、どこから来たかを表す facility と、重さを表す severity が付く。RFC 5424 は facility を 0〜23 の番号で表し、0 がカーネル、4 と 10 がセキュリティと認証、16〜23 が自由に使える local0〜local7 だ[1]。設定ファイルでは、4 を auth、10 を authpriv の名前で書く[2][3]。

syslog の severity（RFC 5424）
番号名前意味
0emergシステムが使えない
1alertすぐに対応が要る
2crit危機的な状態
3errエラー
4warning警告
5notice正常だが、目を留めるべき出来事
6info情報
7debugデバッグ用の細かい情報

二つは、メッセージの先頭の山かっこの中に一つの数でまとめられる。facility の番号に 8 を掛けて severity を足した数で、RFC 5424 の例 <34>1 2003-10-11T22:14:15.003Z mymachine.example.com su - ID47 ... の 34 は、facility 4（認証）と severity 2 を表す[1]。

古い形を書き留めた RFC 3164 は、標準ではなく情報としての文書で、例は <34>Oct 11 22:14:15 mymachine su: ... のように年とタイムゾーンを持たない[4]。RFC 5424 はこれを置き換え、年とタイムゾーンを含む時刻を使う[1]。

rsyslog はテキストに、journald は journal に書く

systemd を使う Linux では、systemd-journald がログを集める。集める先は、カーネルのメッセージ、syslog の関数で出されたメッセージ、journal の独自の方法で出された構造のあるメッセージ、サービスの標準出力と標準エラー、カーネルの監査の記録だ[5]。

journal は /var/log/journal に置けば残り、/run/log/journal に置けば再起動で消える。どちらを使うかは journald.conf の Storage= で決め、auto なら /var/log/journal があるときだけ残す[6]。

journal の項目のうち、名前が「_」で始まるもの（_PID・_UID・_COMM など）は journald が自分で付け、送った側のプログラムが書き換えられない[7]。SYSLOG_IDENTIFIER のような名乗りは送る側が決める。util-linux の logger は、-t で好きな名前を付けて syslog に書ける[8]。テキストのファイルで「sshd」と書かれた行が本当に sshd から出たかは、journal の _COMM や _UID で確かめられる。

rsyslog は、syslog のメッセージを facility と severity で振り分けてファイルに書く。rsyslog が入っていない機械では、ログは journal にしかない。

journalctl は、項目で絞って読む

journal は二進数のファイルなので、journalctl で読む。よく使う絞り方は次のとおり[9]。

  • -u：systemd のユニット（サービス）を指定する
  • -t：syslog の名乗り（SYSLOG_IDENTIFIER）を指定する
  • -p：severity をしぼる。-p warning なら warning とそれより重いもの
  • -S・-U：時刻の範囲。-S today のようにも書ける
  • -b：起動ごとに分ける。--list-boots で起動の一覧が出る
  • -g：本文（MESSAGE）を正規表現で探す
  • -o verbose・-o json：すべての項目を出す

システムの journal を読めるのは、root と、systemd-journal・adm・wheel のグループの利用者だ[9]。

認証の記録の置き場所は、ディストリビューションで違う

認証の記録は、Debian の系統（Ubuntu を含む）では /var/log/auth.log、Red Hat の系統では /var/log/secure に書かれることが多い。ATT&CK も、認証のログの場所としてこの二つを並べている[10]。

どちらも rsyslog の設定の結果だ。rsyslog の Red Hat 向けの設定の見本は、authpriv の全部を /var/log/secure に書き、一般の /var/log/messages からは authpriv を外している[2]。fail2ban の設定でも、認証のログの既定は /var/log/auth.log、Fedora 向けは /var/log/secure になっている[11]。

Debian 12 からは、rsyslog が標準では入らなくなり、ログは journalctl で読むよう案内されている[12]。fail2ban の Debian 向けの設定も、sshd のログを journal から読む[11]。/var/log/auth.log がないときは、まず rsyslog が入っているかを確かめる。

sshd は、認証の結果を1行に書く

OpenSSH の sshd は、既定で facility AUTH、ログの細かさ INFO で書く。説明書は、DEBUG の細かさは利用者のプライバシーを損なうので勧めないとしている[3]。

認証の結果は、ソースの auth.c で一つの形に決まっている。成功は Accepted、失敗は Failed で始まり、方式・ユーザー名・送り元のアドレス・ポートが続く。存在しないユーザーには「invalid user」が付き、その前に「Invalid user」の行も出る[13]。

Invalid user admin01 from 203.0.113.50 port 50122
Failed password for invalid user admin01 from 203.0.113.50 port 50122 ssh2
Failed password for user01 from 203.0.113.50 port 50130 ssh2
Accepted publickey for user01 from 198.51.100.7 port 51022 ssh2: ED25519 SHA256:...

公開鍵での成功には、鍵の種類と指紋（フィンガープリント）が続く[13]。行の頭の時刻・ホスト名・プログラムの名前は、ログを書くソフトと版で変わる。

INFO で残らない失敗もある。auth.c は、パスワードの失敗と存在しないユーザーは INFO で書くが、ある利用者の公開鍵の失敗は、失敗の回数が MaxAuthTries（既定 6）の半分に届くまで VERBOSE で書く[3][13]。上限を超えると「maximum authentication attempts exceeded」の行が出て、接続が切られる[13]。

sudo は、誰が誰として何を実行したかを書く

sudo の行には、実行した人、端末、作業していたディレクトリー、なり代わった相手、コマンドが入る[14]。

user01 : TTY=pts/0 ; PWD=/home/user01 ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx

断られたときは、ユーザー名のあとに理由が入る。sudoers に名前がない「user NOT in sudoers」、その機械で許されていない「user NOT authorized on host」、そのコマンドが許されていない「command not allowed」、パスワードを3回まちがえた「3 incorrect password attempts」などだ[14]。

facility と severity はビルドの設定で決まり、authpriv がある環境では authpriv、成功は notice、拒否は alert が既定になる[14]。ログに入る制御文字は、タブなら「#011」のように「#」と8進数で書かれる[14]。

last と lastb は、wtmp と btmp を読む

ログインとログアウトの記録は、テキストのログとは別の二進数のファイルに残る。last は /var/log/wtmp を読み、ログインした利用者と、再起動（疑似の利用者 reboot）の一覧を出す。lastb は、失敗したログインを記録する /var/log/btmp を読む[15]。

この二つのファイルは、あるときだけ書かれる[15]。wtmp の形は、多くの環境で時刻が 32 ビットのため 2038 年の問題を抱え、SQLite を使う wtmpdb という置き換えが作られている[16]。

auditd は、カーネルが見た出来事を記録する

auditd は、Linux のカーネルの監査の仕組みの、利用者の側の部品で、記録を /var/log/audit/audit.log に書く[17]。何を記録するかは、起動のときに /etc/audit/audit.rules（または /etc/audit/rules.d/）から読まれるルールで決まる[17]。

ルールには、ファイルへの読み書きや属性の変更を見るものと、システムコールを見るものがある。どちらにも「キー」という自由な名前を付けられ、説明書は、調べるときに目的のものだけを選べるようキーを付けるよう勧めている。システムコールのルールは数が増えるほど重くなる[17]。

読むときは ausearch と aureport を使う。ausearch は、キー（-k）、記録の種類（-m）、時刻（-ts）で探し、-i で uid のような番号を名前に直す。一つのシステムコールで出た複数の記録は同じイベントの番号を持ち、まとめて出る。aureport は、認証の試み（-au）やログイン（-l）の集計を出す[17]。

ログは、回転で消え、手で消されることもある

テキストのログは logrotate が区切って古いものを消す。logrotate は日に一度、cron か logrotate.timer で動き、rotate の数だけ古い版を残して、それより古いものを消す（既定は 0）。copytruncate は、写してから元を空にするので、そのあいだの行が抜けることがある[18]。

journal は、ファイルシステムの 10%（上限 4G）を既定の上限とし、超えると閉じた古いファイルから消す。期間で消す MaxRetentionSec= もある[6]。auditd は、ファイルが max_log_file の大きさに届いたときの動きを max_log_file_action で決め、rotate なら num_logs の数だけ残して古いものを消す[17]。

消すのは仕組みだけではない。ATT&CK は、侵入の跡を隠すために /var/log の下のログを消す動きを「Clear Linux or Mac System Logs」（T1070.002）としてまとめている[10]。journal には、鍵を作っておくと改ざんに気づけるようにする封印（Seal=）と、journalctl --verify での確認がある[6][9]。ただし、ファイルごと消されれば、その機械の中には何も残らない。

別の機械へ送れば、手元で消されても写しが残る

ログを送った先の機械には、送り元で消されたあとも写しが残る。syslog の送り方は三つある。

  • UDP の 514 番。確認応答がなく、途中で落ちても気づけない。送り元を確かめる仕組みもない[19]
  • TCP。落ちれば送り直せる。rsyslog の例では 514 番を使う[20]
  • TLS。TCP の 6514 番で、中身を読まれず、相手を確かめられる[20]

UDP と TCP の違いは TCP・UDP の記事に書いた。rsyslog の転送の説明書は、TLS の上の TCP を勧め、送り先が止まっても詰まらないよう待ち行列を付けるよう書いている[20]。送った先を SIEM にすれば、機械をまたいで同じ送り元や同じユーザーを数えられる。

SOC では、失敗の連続・見慣れない sudo・途切れを見る

Linux のログで SOC が見るのは、主に三つの変化だ。

一つ目は、同じ送り元からの sshd の失敗の連続と、そのあとの成功。「Invalid user」の行が続くなら、ユーザー名を推測している動きかもしれない。SIEM の検知ルールの記事の Wazuh と Elastic のルールは、この順番を見ている。

二つ目は、見慣れない sudo。ふだん sudo を使わない利用者の行、ふだんと違う時刻、COMMAND に見慣れないプログラムが入った行、「NOT in sudoers」の拒否の行だ。

三つ目は、ログの途切れ。送られてくるはずの機械から届かなくなる、ファイルが急に小さくなる、時刻に穴が開く。故障のこともあれば、ログを消したり止めたりする動きのこともある。途切れは、届いたログの中には出てこないので、届かないことを数えるルールが要る。

自分の環境で確かめる

ここに書いたことは、自分の仮想マシンで確かめられる。試すのは自分の機械か、許された演習の環境だけにする。

  • journalctl -b -p warning：今回の起動で warning より重い行
  • journalctl -S today -g "Failed password|Invalid user"：今日の sshd の失敗
  • logger -p auth.notice -t test "logger test" を送り、journalctl -t test -o verbose で _COMM と SYSLOG_IDENTIFIER を見比べる
  • last -F と sudo lastb：ログインと失敗の記録
  • sudo aureport -au：auditd が入っていれば、認証の試みの集計
  • /etc/logrotate.conf と /etc/logrotate.d/：何日分を残す設定か

次に読む

  • Windows のセキュリティのログには、監査ポリシーで決めたことしか残らない

    Windows のイベントログは、ログの名前とイベント ID で読む。何が残るかは監査ポリシーと Sysmon の設定で決まり、4688 のコマンドラインは既定では残らない。ログオンの種類の読み方、SOC で目を向ける出来事、SIEM への送り方もまとめた。

  • SIEM は攻撃を止めない。ログをつなげて、人に知らせる仕組みだ

    SIEM がするのは、集める・そろえる・つなげる・知らせる・残すまで。止めるのは SOAR などの別の仕組みと人。どのログを入れるかで、見えるものが決まる。
