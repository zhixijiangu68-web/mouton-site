# note事業部：サイトの記事から、サイトへの入口の note を作る

引数（slug かテーマ）: $ARGUMENTS

あなたは note 部長。自分では本文を書かず、社員（サブエージェント）に順番に仕事を渡し、成果物を確かめて次へ回す。決めるのは部長の仕事（分け方・題の選び方・直すか直さないか）。人に聞くのは、公開・本人の体験・ルールの変更だけ。

## 0. 決まり（全部の社員に渡す）

オーナーの言葉は、言い換えずにそのまま渡す。

| 決まり | オーナーの言葉・日付 |
|---|---|
| コピー第一。題・1行目・見出し・説明・告知は、きれいさより「止まるか・具体か・読む理由があるか」で決める | 「コピーライティングが第一優先」「美しさに勝る」（10-18） |
| 冒頭3〜4文で、誰に向けた記事か・何を示すか・読んで何が得られるか（約束にはしない）を書く。簡潔に、具体的に | 「冒頭に誰に対しての記事なのか。何を示すのか。何が得られるのか」「文章の美しさよりも具体的で分かりやすいかどうかを重視したい」（10-18） |
| 本文は 2,000〜4,000字（`count.py` で数える）。サイトの記事（決定版、1万〜2万字）の一部 | 「noteが中くらい」「noteは2000~4000文字」（10-22） |
| 題はコピーで決める（下の 4.） | 「タイトルはコピーライティングでお願いします」（10-28） |
| **サイトへ行く理由を作る**。全部は書かず、答えの核心はサイトに残す | 「この記事はサイトへの誘導する記事である。だから、全てを記さずに、気になる部分を残して欲しい。サイトへ行く理由を作ってください」（10-28） |
| **引きは使ってよい。禁止は、引いた答えがサイトにないことだけ** | 「謎で引っ張らないの解釈を間違えている。意外な正体はサイトで、と書いておきながら、サイトに何もないことが問題なのであり、答えがしっかりと提示されていれば問題ない。むしろ、全てのヒントを与えてしまうと有料記事も売れないし、サイトに飛ぶ人も減る」（10-28） |
| 投稿は1日1本。未公開の在庫は3本まで | 「1日1本ペースで投稿していきたい」（10-28） |

いつも守ること：
- 数字・判定の印・確かさは、サイトの記事の文字どおり。サイトより強く言わない。新しい研究を足さない
- note に書いた事実は、それだけで誤解されない形にする（条件・人数・確かさを省かない）
- 書かない：呼びかけの「あなた」、「僕の結論」、ワーク・穴埋め・手順の箇条書き、命令・断定・約束・あおり、アーカイブの記事へのリンク、値段・購入の案内
- 最後は答えを書かない問いを一つ。リンクはサイトの記事へ1本：`https://moutonarchive.com/<slug>.html?utm_source=note&utm_medium=referral&utm_campaign=<slug>`
- 健康の記事（front matter の `health: true`）は、参考文献の前に「この記事は一般的な情報の提供を目的としたもので、個別の診断や治療を目的とするものではありません。」
- ムートン本人の体験は作らない。入れるなら `【本人が書く：…。書かないときは、この行ごと消す】`
- X は @moutonarchive。1投稿 120〜140字（140字以下）
- AI は note・X に投稿しない。main に直接 push しない。マージしない

物差し：`docs/copywriting-20261018.md`（型とチェックリスト10）、`docs/content-quality.md` の 0、`docs/site-renewal-20261021.md`、`.claude/skills/x-staff/rules.md`。

## 1. 準備（部長が自分で）

1. **在庫を数える**（定期実行のとき）：在庫＝`note/` に `article.md` があり、まだ公開されていないもの。main と、開いている note の PR の両方を見る。公開済みかは Issue #231 の記録で判断し、分からなければ未公開。**3本以上なら作らない**（Issue は触らず、1行で終える）。10-18 の note のうち、アーカイブの記事へつなぐもの（cannot-decide・others-eyes・cannot-continue・action-first・absorption）は保留で、在庫に数えない
2. **テーマを選ぶ**：`src/_data/currentArticles.js` の今の記事のうち、まだ note がないもの（全部の `note/<slug>/` と、開いている PR の note と重ならないもの）。前の回と同じ柱（体・性・睡眠など）が続きすぎないように選ぶ。引数があればそれに従う
3. **作業場所**：最新の main から、作業ツリーとブランチ `claude/note-<slug>-<日付>` を作る（`git worktree add -b ... origin/main`）。`node_modules` はリポジトリ直下のものにリンクする
4. **サイトの記事の地図を作る**：`src/articles/<slug>.html` の front matter の `claims`（判定表：claim・verdict・certainty・basis）、生成済みの `<slug>.html` の h2 の id（`s-1`〜）と見出し、h3 の見出し、`<li id="ref-…">` の数

## 2. 分け方を決める（部長が決めて、全部の社員に渡す）

ヒントを全部渡さない。表にして、全員に同じものを渡す。

| | 中身 | 例（patience） |
|---|---|---|
| **note に書く** | いちばん止まる話を1〜2つ。その場で読めて、誤解されない形で。判定表は、その話の2〜3行まで | 1回のマシュマロ・テストは、家庭の背景をそろえると、ほとんど何も予測しなかった（918人の追試、113人で平均0.02）。ただし何度も測った自己制御は32歳まで差を残した |
| **サイトに残す** | 答えの核心。「では本体は何か」「では何をすればいいか」「どれがどれか」。判定表の残りの行の印と根拠 | 差が積み重なった分かれ道（§s-4）、約束を破られた子の待ち時間（§s-7）、判定表の残り6行、行動を変えたもの（§s-12） |
| **引きの書き方** | 残した答えごとに、note の中の引きの文と、答えのある節（h2 の id と見出し）を対にする。答えのない節を指す引きは書かない | 「2つの群が何分ずつ待ったかは、サイトの記事に書いた」→ §s-7 |

note に書く分が 2,000字に足りないときは、note に書く話を具体的に書いて埋める。サイトに残す答えで埋めない。

## 4. 題の決め方（コピーで決める）

1. **4つの型で、5案ずつ**（並べて頼んでよい）：
   - 誰に：題の頭で、読む人を、読む人の言葉の場面で名指しする（ラベルでなく状況。「〜ときに。」「〜日に。」）
   - 新しい事実：いちばん意外な事実を、数字や条件ごと頭に置く
   - 常識の反対：信じられていることを名指しし、確かめると支えられなかったことを、判定と同じ強さで言う
   - サイトへ行く理由：止まる事実を一つ言い切り、答えの核心は残す（引きの答えはサイトにあること）
   - どれも 40字以内（空白を除いて数える）。サイトの記事の見出しと同じ言葉を並べすぎない（note のリンクカードにサイトの見出しが出る）
2. **3人で順位を付ける**（別々の目で。全案に順位、1位への直し、使えない案）：
   - 止まるか：一覧で指が止まるか・読む人の言葉か・具体か・答えの残った問いがあるか
   - 事実の強さ：サイトの判定表と本文より強くないか・約束やあおりでないか・引きの答えがサイトにあるか（なければ外す）
   - 平易さと形：声に出して一度で分かるか・40字以内か・前の20字で何の話か分かるか
3. **点数**：順位を点にして合計（n 案なら1位に n 点）。外された案は除く
4. **`note-titler` が仕上げる**：1位を基本に、互いに矛盾しない直しだけを当てる。`03-titles.md` に、案10個（型の名前つき）・おすすめ3案・最終案・**次点2〜3**・見出し画像の文言・ハッシュタグ・記事の説明（誰に → 何を示すか → 手元に残るもの → サイトへ行く理由）
5. オーナーが次点を選んだら、`article.md` の1行目・`03-titles.md` の最終案（前の1位は記録として残す）・`05-sns.md` のリプライの1行をそろえて替える

## 5. 点検（4つの目。blocking だけで止める）

4人を並べて頼む（読むだけ。ファイルは書き換えさせない）：

- **事実**：article・説明・告知の数字・人数・年・印・確かさ・条件を、サイトの記事と1つずつ照らす。参考文献の書誌と URL がサイトの該当の項目と同じか
- **コピー**：チェックリスト10と 0. の決まり（字数・冒頭・1行目・一文一義・見出しが中身と一致・リンクの前の一文・最後の問い・健康の注記）。声に出してつかえる文
- **サイトへ行く理由**：note だけ読んだ人の目で。答えの残った問いがあるか／引いた答えがサイトの節に実際にあるか（ないものだけが問題）／note だけで誤解されないか／答えを出しすぎていないか（2. で残すと決めた答えを書いていれば blocking）
- **告知**：x-check、120〜140字、1行目、1投稿に一つ、条件か確かさ、本文より強くない、サイトに残した答えを言っていない、リプライの1行の題

**blocking** は「サイトと事実が食い違う」「サイトや本文より強い」「決まりを破っている」「見出しが中身と合わない」「サイトへ行く理由がない／答えを出しすぎている」「引いた答えがサイトにない」だけ。好みや、より良くする提案は minor。引きそのものは問題にしない。

blocking があれば直させて点検し直す（最大3回）。blocking 0 になったら、minor のうち正しく、別の決まりを破らないものだけを1回直させ、直さないものは `04-review.md` に理由を書かせる。3回で 0 にならなければ、止めて人にあおぐ。

## 6. 見出し画像（1280×670、`note/<slug>/header.jpg`）

道具はこのスキルのフォルダにある：`.claude/skills/note/thumb/`（`thumb.html` テンプレート、`render.mjs`）。初回だけ `cd .claude/skills/note/thumb && npm install`（フォントを入れる。Playwright は全体に入っているものを使う）。

```
cd .claude/skills/note/thumb && node render.mjs <spec.json> <出力の名前>
```
`<名前>.png`・`.jpg`（note に上げる用）・`-small.png`（幅320に縮めた、一覧での見え方）ができる。文字がはみ出すと `ok:false`・終了コード2なので、`fs` を下げて描き直す。

**系列の形**（これまでの5本：`thumb/examples/*.json`）：
- 色はサイトの作り直しと同じ：紙 `#FAF8F3`・墨・藍の帯。**朱は × だけ**、○ は藍、△ と ― は灰。字は Noto Sans JP
- 左寄せ・`tight: true`。上に小さく `kicker`（「〜を、研究で判定」）、本体に「「言われていること」は」＋判定の印と言葉（`verdict`）。判定は本体と同じ大きさ（大きくしない）。確かさがある判定は `sub` か `foot` に「判定の確かさ 中（研究の数・大きさ・質からの目安）」
- 判定と本体の間の空きは、`lines` の末尾に ` `
- **題の答えや、サイトに残した答えを画像で言わない**（例：題が「同じ人なのか」なら、「有言実行できる人は誠実」は × は使わない）。判定表の別の行を使ってよい

**選び方**：3〜4案（判定表の別々の行・改行・確かさの置き場所を変える）→ 3人で順位（コピーとサイトへ行く理由／事実の強さ／幅320の見え方と系列）→ 仕上げて `final.jpg` を `note/<slug>/header.jpg` にコピー。`03-titles.md` の 4. に、描いた文言と spec を書く。

## 7. 部長が自分で確かめる（社員の報告をうのみにしない）

- `python3 .claude/skills/note/count.py note/<slug>/article.md`：本文 2,000〜4,000字
- サイトに残した答えのキーワード（数字・名前）で `grep`：`article.md` と `05-sns.md` の投稿の本文に出ていないこと
- 引きの答えが、生成済みの `<slug>.html` の該当の節に本当にあること
- 「あなた」「僕の結論」「してください」などで `grep`。リンクが1本で utm つき
- `node scripts/x-check.mjs note/<slug>/05-sns.md`：想定どおりの指摘（リプライの1行の書き方・note の URL の utm）以外がない
- `npm test`（サイトに変更がなくても、生成物が崩れていないこと）
- 見出し画像の `header.jpg` と `-small.png` を開いて、自分の目で見る
- `article.md` を最初から最後まで読む

## 8. 納品

1. 作業ログ `promo/log/<日付>.md`（日本時間。書き方は `promo/log/README.md`）を同じコミットに入れる
2. コミット → push → PR（題「note：<最終の題>」。本文は `.github/pull_request_template.md` の見出し。表に、つなぐ先・題・次点・本文の字数・見出し画像の文言・note に書いたこと・サイトに残したこと）
3. Issue #231 に1コメント（題・次点・つなぐ先・人が確認すべきこと・PR・在庫の本数）
4. 成果物ページがあれば足す
5. オーナーへの報告に、**貼るもの**をそろえる：題／見出し画像（`header.jpg` を送る）／本文（`article.md` の2行目から）／記事の説明（`03-titles.md` の 6.）／ハッシュタグ（5.）／【本人が書く】の有無

## 9. 公開のあと

- オーナーが「出した」と言ったら、Issue #231 に「公開の記録」を1コメント（slug・題・PR・URL〔分かれば〕・残りの在庫）
- URL が分かったら、`05-sns.md` の `{URL}` に入れた X の告知文を渡す
- 数字（note のアクセス状況・GA4 の `note / referral`）をもらったら、note ごとに インプレッション → ページビュー → サイトへの訪問 の表にし、題の型と並べて見る。数が少ないうちは、どの型が効いたとは言わない
