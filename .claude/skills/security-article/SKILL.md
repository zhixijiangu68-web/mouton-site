# セキュリティの記事と資料を作る

引数（テーマ）: $ARGUMENTS

正の決まりは `docs/security-renewal-20261104.md`（CLAUDE.md の先頭の節）。このスキルの決まりは `rules.md`、記事と資料の形は `templates.md`。**作りながら直していく**スキルなので、1本作るたびに、うまくいかなかったことを下の「改良の記録」に1行足し、必要なら手順・決まり・型を直す。

## 0. 準備
- テーマが空なら聞いて止まる。テーマから英小文字とハイフンの slug を決める（例：`ids`）。`src/articles/<slug>.html` がすでにあれば別の slug
- 柱（`pillar`）を決める：`ctf`（演習・CTF の記録）／`vuln`（脆弱性・事件の読み解き）／`defense`（守る側の手順・道具・選び方）。製品比較や選び方は `defense`
- 記事の形を `templates.md` から選ぶ（A 道具と選び方／B 脆弱性・事件／C 演習の記録）
- 作業用のフォルダはスクラッチパッドの `<slug>/`。リポジトリには作業メモを入れない

## 1. 調べる（3つの目で、並行して）
サブエージェントを3人、同時に動かす（Agent ツール、バックグラウンド）。それぞれに `rules.md` の「調べるときの決まり」を渡す。形 A なら：
1. **仕組みと製品（無料・オープンソース）**：公式サイト・公式リポジトリ・公式ドキュメント・リリースノート
2. **仕組みと製品（商用・クラウド）**：メーカーの公式の製品ページ・データシート・ドキュメント。第三者の評価があれば年と出所
3. **重要性と、どこを見るべきか**：NIST・CIS・IPA・JPCERT/CC・NISC・MITRE などの一次資料、統計は最新版と年（M-Trends、IBM Cost of a Data Breach、IPA 10大脅威、警察庁 など）、合法な演習の入口

形 B は「公式の発表（CISA KEV・JPCERT/CC・IPA・メーカーの告知）／技術の解説（一次の分析）／検知と防ぎ方」、形 C は「演習の公式の説明／自分の記録（オーナーのメモ）／使った道具の公式ドキュメント」の3つに分ける。
- 各自 WebSearch は20回まで。WebFetch は通らないことが多いので、検索の結果で確かめ、要約でしか確かめられないものには【要約のみ】と印を付けさせる

## 2. 事実の一覧（factsheet）
3人の結果から、確かめた事実だけを並べた一覧を作る（スクラッチパッドの `<slug>/factsheet.md`）。各行：事実・数字・日付・出典の URL・確かめ方（公式で確認／要約のみ）。**【要約のみ】の数字は、記事の主張の根拠にしない**（使うなら「〜とされる」で、出典の種類を書く）。食い違う数字は両方と出所を書き、記事では新しい一次資料のほうを使う。

## 3. 記事を書く（`src/articles/<slug>.html`）
- `layout: renewal-article.njk`、`pillar`、`title`（末尾に「 — ムートン」）・`headline`・`subtitle`・`description`（80〜120字）・`date`・`updated`・`related`
- 形は `templates.md`。見出し（h2）は結論の一文。最後は問いを一つ（`<p class="rn-question">`）。参考文献は番号つき（`<section class="rn-refs">`、本文に `<a href="#ref-N">[N]</a>`）
- 本文は今の決まりで1万〜2万字（`npm test` が数える。長さと型はオーナーが決めるまでの仮）。**最初から1万2千字を目安に組む**（節の数と、表・例の置き場所を先に決める）
- 下書きはスクラッチパッドで書き、出典は `[[key]]` と書いておく。`refs.tsv`（key・説明・URL・リンクの文字のタブ区切り）を作り、`node .claude/skills/security-article/number-refs.mjs <下書き> <refs.tsv> src/articles/<slug>.html` で番号をつける（出てくる順。判定表の refs も番号になる）
- 設定やルールの例は `<pre><code>` で書く（390px で折り返す。renewal.css）。例は演習用だけ（宛先は example.com や 192.0.2.0/24）。動かして確かめていない例は、そう書く
- 製品の比較は、表と言葉の両方で。**宣伝の数字（検知率○％など）は「メーカーの発表」と書き分ける**。値段は公式の価格ページにあるものだけ、日付つき
- 安全の決まり（`rules.md` の1〜5）を守る。記事の中で、読む人にも「試すのは自分の環境と許可された演習の中だけ」と書く

## 4. 資料を作る（`materials/<slug>.md`）
記事とは別の、手元に置いて見返す1枚もの。`templates.md` の「資料の型」で：要点5つ・比較表・選ぶとき／運用するときのチェックリスト・用語・出典。記事と数字が食い違わないようにする（資料の数字はすべて記事にもある）。オーナーが求めたら、同じ中身を Claude Docs のドキュメントにもする。

## 4.5 理解度テストを作る（`src/_data/understanding/<slug>.json`）
いまの記事には8〜10問が要る（ないとスモークテストが落ちる）。選択肢は4つ、`answer` は 0〜3 をばらけさせる、`why` に解説、`section` は記事の h2 と同じ文字。問題は記事に書いたことだけから作る。

## 5. 点検（3つの目で、並行して）
サブエージェントに反証させる：
- **事実**：記事と資料の数字・日付・版・製品の名前を、factsheet と出典に一つずつ照らす
- **安全の決まり**：`rules.md` の1〜5に当たる書き方がないか（悪用の手順・実在の宛先・未修正の脆弱性の手口）
- **コピーと読みやすさ**：CLAUDE.md の文章のルール、`docs/content-quality.md` の0、一文が長すぎないか、専門用語を初出で言い換えているか
must（直さないと出せない）と should を直し、直したことを確かめる。

## 6. 組み込みと PR
- `src/_data/currentArticles.js` に slug を足す（足さないとアーカイブ扱い）
- `npm run build` → `npm test` → `npm run lint:writing -- <slug>`。スモークテストは Playwright のリンクを作ってから `node --test tests/browser-smoke.mjs`
- シェア用の画像：`cd scripts/og && npm install && node make.mjs`（Chromium は `CHROME_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome`）。作り直された既存の画像は戻し、新しい1枚だけコミット
- `promo/log/YYYY-MM-DD.md` に作業ログ（依頼・やったこと・判断・確かめたこと・見つけた問題・残り）
- 枝を作ってコミット・push・PR（テンプレートに沿う）。マージ・公開はオーナー

## 人に聞くこと
公開の判断、オーナー本人の体験や演習の記録、製品を勧めるかどうか（このサイトは特定の製品を勧めない。選ぶ観点を渡す）。それ以外は妥当な案で進め、あとで「何をどう判断したか」を報告する。
