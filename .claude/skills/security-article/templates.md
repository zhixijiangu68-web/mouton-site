# 記事と資料の形（security-article）

長さと型はオーナーが決めるまでの仮。直したら、ここを直す。

## 記事の形 A：道具と選び方（`pillar: defense`。例：IDS、EDR、WAF、パスワード管理）
1. 冒頭（2〜3段落）：その道具がないと何が起きるか（一次資料の数字か、公開された事件を一つ）→ この記事で分かること
2. 判定表（任意）：「よく言われること」を、公式の資料と研究で判定（front matter の `claims`。○ 支持・× 否定・△ 弱い・― 証拠なし）
3. 仕組み：何を見て、何を知らせるか。近い道具との違い（表）
4. なぜ大事か：気づくまでの日数などの数字と、基準（NIST・CIS）での位置
5. 種類ごとの製品：無料・オープンソース／商用／クラウド。表（方式・遮断・置き場所・ルールの更新・料金の形）と、製品ごとの短い節
6. どこを見るべきか：選ぶとき（置き場所・検知の方式・暗号化・処理能力・ルール・連携・運用の手間・料金）と、運用するとき（誤検知・チューニング・アラートの見方・ログの保存）
7. 手を動かして学ぶ：合法な演習の入口（自分の仮想環境・公開された PCAP・学習サイト）。「試すのは自分の環境と許可された演習の中だけ」の一文
8. 最後の節：分かったこと・分かっていないこと（時点の注意）→ 問いを一つ

## 記事の形 B：脆弱性・事件の読み解き（`pillar: vuln`）
何が起きたか（公式の発表・日付）→ 影響を受ける版 → 修正と回避策（先に）→ 仕組み（悪用の手順は書かない）→ 見つけ方（検知・ログの見どころ）→ 同じことを防ぐには → 問い

## 記事の形 C：演習・CTF の記録（`pillar: ctf`）
演習の名前と公式の説明（許可された環境であること）→ 目標 → 考えたこと・試したこと（オーナーの記録から）→ つまずき → 学んだ仕組み → 守る側から見ると → 問い。答えそのもの（フラグ）は、演習の決まりで公開してよいものだけ

# <テーマ>：手元に置く資料（YYYY-MM-DD 時点）
