# 決まり（security-article）

正は `docs/security-renewal-20261104.md`。食い違ったら、あちらが先。

## 安全の決まり（書く内容）
1. 試すのは、自分の環境と、許可された演習（CTF・学習用の演習）の中だけ。他人のシステムやサービスには、許可なく試さない（不正アクセス禁止法）。記事の中でも、読む人にそう書く
2. まだ修正されていない脆弱性の悪用の手順は書かない。脆弱性は、仕組み・見つけ方（検知）・防ぎ方を中心に書き、公開された修正・回避策を先に書く
3. 道具やコードを載せるときは、演習の環境で使う形にとどめる。実在の他人の環境を狙う形（実在のドメイン・IP・認証情報）を書かない。例のアドレスは RFC 5737 の文書用（192.0.2.0/24 など）と example.com
4. 弱点を見つけたら公開せず、作った会社や窓口（日本なら IPA の届出の窓口）に知らせる
5. 製品を勧めない。比べる観点と事実を渡し、選ぶのは読む人。宣伝の数字は「メーカーの発表」と書き分ける。PR・アフィリエイトを付けない

## 調べるときの決まり
- 事実・数字・日付・版は、公式の発表と一次資料（CISA・NIST・JPCERT/CC・IPA・NISC・警察庁・メーカーの公式・プロジェクトの公式リポジトリ）で確かめ、出典の URL を付ける
- 検索の要約でしか確かめられなかったものは【要約のみ】。記事の主張の根拠にはしない
- 統計は最新版を使い、年と調べた対象（どの国・何件）を書く
- 確かめられないことは書かない。古くなりやすいこと（版・価格・提供の状況）には「〇年〇月時点」を付ける

## 文章
- 日本語、一人称は「僕」。専門家ではなく、勉強している一人として書く。言い切れないことは言い切らない
- 専門用語は初出で言い換える（例：IDS（侵入検知システム。通信やログを見て、攻撃らしいものを知らせる仕組み））
- 一文は短く（平均35字前後、80字を超えない）。見出し（h2）は結論の一文
- 命令・あおり（「必須」「今すぐ」「危険！」）を使わない
