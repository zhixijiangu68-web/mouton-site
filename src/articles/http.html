HTTP は、クライアントが要求を一つ送り、サーバーが応答を返す決まりで、一つひとつの要求は前の要求と切り離して扱われる。ログインの状態のような前後のつながりは Cookie が運ぶので、Cookie の属性と、通り道で中身を守る HTTPS が、Web の守りの土台になる。HTTP は TCP・UDP の記事のポート 80 と 443 の上で動き、HTTPS は TLS の記事の TLS の上で HTTP を送る。例のアドレスとドメインは、文書用のもの（203.0.113.0/24、example.com）だけを使う。

HTTP は、要求を一つ送り、応答を一つ受け取る

RFC 9110 は、HTTP を「状態を持たない、要求と応答のプロトコル」と定めている。それぞれの要求はそれだけで意味が分かるように作られ、サーバーは、前に何が来たかを HTTP の仕組みとしては覚えていない[1]。

HTTP/1.1・HTTP/2・HTTP/3 は、どれも RFC 9110 の同じ意味の決まりに従い、違うのは送り方だ[1]。HTTP/1.1 は文字の行で要求を書いて TCP で送る[2]。HTTP/2 は同じ中身を二進数の枠（フレーム）に詰め、一つの接続で複数のやりとりを並行して運ぶ[3]。HTTP/3 は UDP の上の QUIC を使う[4]。ポートを書かなければ、http は TCP の 80 番、https は 443 番につなぐ[1]。

要求の1行目は、メソッドとパスとバージョン

HTTP/1.1 の要求は、メソッド・要求の対象・バージョンを空白で区切った1行から始まり、ヘッダーが1行ずつ続く[2]。http://www.example.com/articles/http.html?ref=top を開くと、GET /articles/http.html?ref=top HTTP/1.1 と Host: www.example.com が送られる。要求の対象は URL のパスと「?」のあとのクエリだけで[2]、「#」から後ろ（フラグメント）はブラウザーの中で使い、サーバーには送らない[1]。

ホストの名前は Host ヘッダーで送る。RFC 9112 は、HTTP/1.1 の要求に Host を入れるよう求め、Host がないか2つ以上ある要求には 400 を返すよう決めている[2]。Host のおかげで、一つのサーバーが複数のドメインを受け持てる。そのぶん、キャッシュを汚したり、要求を別のサーバーへ向けさせたりする攻撃の的にもなる[1]。

URL は秘密を守る場所ではない。サーバーやプロキシやブラウザーの多くが URL をログに残し、表示するので、RFC 9110 は、知られては困る情報を URL に入れないよう勧めている[1]。クエリに載せたものは、アクセスログにそのまま残る。

メソッドは、要求の目的を表す

メソッドは、要求で何をしたいかを表す。RFC 9110 は8つのメソッドを定め、汎用のサーバーには GET と HEAD への対応を求めている。実装していないメソッドには 501、その対象に許していないメソッドには 405 を返すのがよいとされる[1]。

RFC 9110 の主なメソッド
メソッド目的安全べき等
GET対象の中身を受け取る○○
HEADGET と同じだが、本文を受け取らない○○
POST送った中身（フォームの入力など）を、対象に処理させる――
PUT対象を、送った中身で作る・置き換える―○
DELETE対象を消す―○

ほかに CONNECT・OPTIONS・TRACE がある。「安全」は、サーバーの状態を変えることを求めない読むだけのメソッドで、GET・HEAD・OPTIONS・TRACE が当たる。「べき等」は、何度送っても1回と同じ結果を求めるメソッドで、安全なものと PUT・DELETE が当たる[1]。巡回のプログラムや先読みは、安全なメソッドなら害がないとみなしてリンクを GET する。そのため RFC 9110 は、page?do=delete のような消す操作を、GET では動かさないよう求めている[1]。

ステータスコードは、最初の1桁で結果の種類が分かる

応答の1行目には、3桁のステータスコードが入る。範囲は100〜599で、最初の1桁が結果の種類を表す。クライアントは知らないコードでも種類は理解し、たとえば 471 は 400 として扱う[1]。

ステータスコードの5つの種類（RFC 9110）
種類意味例
1xx受け取った。処理を続けている100 Continue
2xx成功した200 OK
3xx完了には、別の動きが要る（転送など）301・302・304
4xxクライアントの側の誤り400・401・403・404
5xxサーバーの側の誤り500・501・503

301 と 302 は転送で、行き先は Location ヘッダーに入る。401 は認証の情報がないこと、403 は要求を理解したうえで断ることを表す。RFC 9110 は、対象があること自体を隠したいサーバーが、403 の代わりに 404 を返してよいとしている[1]。ログの 404 は、その URL に何もないとは限らない。

ヘッダーは、要求と応答に添える情報

ヘッダーは「名前: 値」の行で、名前の大文字と小文字は区別しない[2]。守りの面でよく見るのは、Host のほかに User-Agent と Referer だ。

User-Agent は、要求を送ったソフトの名前と版を、クライアント自身が名乗るヘッダーだ。RFC 9110 は、細かすぎる値は利用者の見分け（フィンガープリント）に使われると注意し、別のソフトを名乗る場合にも触れている[1]。curl は既定で curl/ と版の番号を送り、-A で好きな文字列に変えられる[5]。Referer は、どのページから来たかを表すが、すべての要求に付くわけではない[1]。

RFC 9110 は、メソッド・URL・ヘッダー・本文のどれも、攻撃する側が好きに作れると書いている[1]。要求の値は、どれもそのまま信じない前提で扱う。

Cookie は、状態を持たない HTTP に前後のつながりを足す

Cookie は、サーバーが応答の Set-Cookie で名前と値を渡し、ブラウザーが次からの要求の Cookie ヘッダーで返す仕組みだ。RFC 6265 の例では、サーバーが Set-Cookie: SID=31d4d96e407aad42 を返し、ブラウザーは次から Cookie: SID=31d4d96e407aad42 を送る[6]。

多くのサーバーは、意味のない番号（セッション ID）を Cookie に入れ、それを鍵にしてサーバーの側の情報を引く[6]。サーバーから見ると、正しいセッション ID を送ってきた要求が、ログインした本人の要求になる。RFC 6265 は、ここから来る弱点を挙げている[6]。

  • ブラウザーは、他のサイトに仕向けられた要求にも Cookie を付ける。これがクロスサイト・リクエスト・フォージェリ（CSRF）の土台になる
  • 攻撃者が自分の持つセッション ID を相手のブラウザーに押し込み、相手がログインしたあとで同じ ID を使う「セッション固定」がある
  • Cookie の中身を暗号化して署名しても、別のブラウザーへ移されたり、あとで使い回されたりするのは防げない

Cookie には、残す期限（Expires・Max-Age）と、送る先のホスト（Domain）とパス（Path）も付けられる。ブラウザーが送り返すのは名前と値だけで、サーバーは、どの属性で作られたかを Cookie ヘッダーからは知れない[6]。

Cookie の属性で、送る先と読める相手をしぼる

Secure・HttpOnly・SameSite の三つの属性で、セッション ID の Cookie が漏れる道をしぼれる。

Secure を付けた Cookie は、TLS のような守られた通り道の要求にしか付かない。RFC 6265 は、HTTPS のウェブメールが Secure を付けていないと、通り道の攻撃者が平文の要求を起こさせて Cookie を盗める、という例を挙げている。ただし Secure は、平文の通り道から Cookie を上書きされることまでは防がない[6]。HttpOnly を付けた Cookie は、ページのスクリプトのような HTTP 以外の方法からは読めない[6]。

SameSite は RFC 6265 にはなく、改訂の草案（draft-ietf-httpbis-rfc6265bis）が定めている。Strict は、同じサイトからの要求にだけ Cookie を付ける。Lax は、他のサイトからのリンクでページを開くときにも、GET のような安全なメソッドなら付ける。None はどの要求にも付け、Secure のない None の Cookie は受け付けられない[7]。草案は、SameSite だけに頼らず、CSRF トークンのようなサーバー側の対策と組み合わせるよう勧めている[7]。

HTTPS は、TLS の上で HTTP を送り、HSTS で平文に戻らないようにする

https の URL は、TLS でつなぎ、相手が本物のサーバーであることを確かめ、中身を読まれず書き換えられない状態で HTTP を送ることを意味する[1]。TLS の仕組みは TLS の記事に書いた。TLS がなければ、Cookie は平文で流れる[6]。

HSTS は、サイトが「HTTPS でしかつながない」ことをブラウザーに覚えさせる仕組みで、RFC 6797 が定めている。サーバーは HTTPS の応答に Strict-Transport-Security: max-age=31536000 を付ける。max-age は覚えておく秒数で、31536000秒はおよそ1年だ。覚えたブラウザーは、そのホストの http の URL を、つなぐ前に https に書き換え、証明書に誤りがあれば、利用者に「続ける」を選ばせずに接続をやめる[8]。

弱点は最初の1回だ。まだ覚えていないブラウザーが http で最初につなぐと、その1回は守られない。RFC 6797 は、ブラウザーに最初から HSTS のサイトの一覧（プリロードの一覧）を入れておく方法で補えると書いている[8]。

アクセスログには、一つの要求が一行で残る

Apache httpd の Combined Log Format と nginx の既定の combined では、一つの要求が、送り元・時刻・要求の1行目・ステータスコード・大きさ・Referer・User-Agent の1行で残る[9][10]。文書用のアドレスで書くと、次のようになる。

203.0.113.25 - - [07/Nov/2026:21:58:03 +0900] "GET /articles/http.html HTTP/1.1" 200 5120 "https://www.example.com/" "curl/8.5.0"

Apache の説明書によると、最初の欄の送り元は、間にプロキシがあればプロキシのアドレスになる。「-」は情報がないことを表し、引用符の中が要求の1行目、そのあとがステータスコードと応答の大きさだ[9]。HTTPS は通り道で中身を隠すが、サーバーのログには、ほどいたあとの要求が残る。

ログそのものも守る対象だ。RFC 9110 は、アクセスログを個人の情報として安全にしまい、要らなくなった IP アドレスやクエリを消すよう勧めている。ログに残った要求の値が、あとで監視の道具の中で命令として解釈されないよう気をつけることも求めている[1]。

SIEM では、数の変化と見慣れない要求を見る

アクセスログを SIEM に集めると、1行ずつでは見えない数の変化と、ふだんと違う要求が見える。

  • 4xx の急増。同じ送り元から短い時間に 404 が続くなら、ないページを探している動きかもしれない。ログインのパスで 401 や 403 が増えるなら、パスワードを繰り返し試している動きかもしれない
  • 5xx の急増。故障のこともあれば、想定していない要求で処理に失敗していることもある
  • 見慣れないパスの連続。自分のサイトにない管理画面のパスや、RFC 9110 が注意を促す「..」を含むパス[1]
  • 使っていないメソッドや、極端に長い URL。長すぎる URL には 414 を返す決まりがある[2]

ログの値には、偽れるものがある。User-Agent は相手が名乗った名前で[5]、送り元はプロキシや中継を通せば中継のアドレスになる[9]。User-Agent だけで安全と決めず、送り元の数・時刻の並び・ステータスコードの変化を合わせて見る。

自分の環境で確かめる

HTTP のやりとりは、自分のパソコンの中でサーバーと curl を動かせば見られる。試すのは自分の機械か、許された演習の環境だけにする。

python3 -m http.server --bind 127.0.0.1 8000 で、小さなサーバーが動く。既定ではすべてのインターフェースで待ち受けるので、--bind 127.0.0.1 で自分の機械の中だけにする。Python の説明書は、本番に使うことは勧めていない[11]。

別の端末で curl -v http://127.0.0.1:8000/ を送ると、「>」の行に送ったヘッダー、「<」の行に受け取ったヘッダー、「*」の行に curl の説明が出る[5]。僕の手元（curl 8.5.0）では、GET / HTTP/1.1・Host: 127.0.0.1:8000・User-Agent: curl/8.5.0 が送られ、HTTP/1.0 200 OK が返った。サーバーの端末には 127.0.0.1 - - [07/Nov/2026 10:28:01] "GET / HTTP/1.1" 200 - の行が出た。ないパスでは 404 が、-X POST では、POST を実装していないこのサーバーから 501 が返った。

自己署名の証明書で HTTPS のサーバーを動かし、--cacert でその証明書を信頼させて curl -v を送ると、「*」の行に TLS 1.3 の取り決めと ALPN の様子が出て、そのあとに HTTP の要求と応答が出る。-v の出力には認証の情報のような秘密が含まれうるので、人に見せるときは消す[5]。
