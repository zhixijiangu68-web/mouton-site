DNS は、example.com のような名前を、通信に使う IP アドレスに変える仕組みだ[1][2]。名前は右から読む木の形で管理され、利用者の代わりにフルサービスリゾルバーがルート・TLD・権威サーバーの順に問い合わせ、答えを TTL の秒数だけ覚えておく。ルーティングの記事で見た 2024年6月の 1.1.1.1 の事例は、経路の問題が、このリゾルバーに届く道をふさいだものだった。例には example.com と、文書用のアドレスとプライベートアドレスを使う。

名前は、右から読む木になっている

DNS の名前は一本の木で、右端が根（ルート）、左へ行くほど枝の先になる。RFC 1034 は名前空間を木の形と定め、木の一つひとつの点（ノード）にラベルが付き、ノードの名前は、そこから根までのラベルを並べたものだとしている[1]。www.example.com なら、根の下に com、その下に example、その下に www がある。

ラベルは0〜63オクテットで、長さ0のラベルは根のためだけに使う。名前全体は、通信で送る形で255オクテットまでだ[2][3]。完全な名前は根の空のラベルで終わるので、正式には「www.example.com.」と最後に点を付けて書く。ふだんの表示では、この点を省く[3]。大文字と小文字は区別せずに比べる[1]。

ある名前が別の名前の下にあるかは、ラベル単位で末尾を比べて決める。RFC 9499 の例では、ooo.example.com は oo.example.com の下にはない[3]。文字列の末尾が一致するかだけで判断すると、この区別を誤る。ログを検索するときや、許可する名前の一覧を作るときも同じだ。

木はゾーンに区切られ、委任でつながる

名前の木は、管理する組織ごとの「ゾーン」に区切られ、親のゾーンが子のゾーンの担当サーバーを示すことでつながっている。RFC 1034 は、木の隣り合うノードの間に切れ目を入れ、切れ目で囲まれた一続きの部分を一つのゾーンとし、組織は自分のゾーンの中を自由に変え、さらに下を別のゾーンとして任せられる、と書いている[1]。

この「任せる」ことを委任と呼ぶ。委任は、親のゾーンに、子の名前の NS レコード（そのゾーンを担当するサーバーの名前）を置くことで起きる[3]。根のゾーン（ルートゾーン）の一段下が、com や jp のような TLD のゾーンで、example.com のゾーンは com のゾーンから委任される[3]。ルートゾーンを答えるサーバーは、互いに独立したルートサーバーの運用者が出している[3]。

ゾーンの中身を自分の情報として持ち、ほかに聞かずに答えられるサーバーを権威サーバーと呼ぶ。権威サーバーは、自分のゾーンの答えに AA（Authoritative Answer）の印を付け、子のゾーンについて聞かれると、子の担当サーバーを示す紹介（referral）を返す[3]。担当サーバーの名前が子のゾーンの中にあると（ns.example.com が example.com を担当するなど）、そのアドレスを引くのに、そのサーバー自身に聞かなければならなくなる。これを避けるため、親のゾーンは紹介にそのサーバーのアドレスを添える。このアドレスをグルーと呼ぶ[1][3]。

引く仕事は、スタブリゾルバーとフルサービスリゾルバーで分かれる

手元の機器は名前を自分では引ききらず、近くのフルサービスリゾルバーに頼む。RFC 1123 は、リゾルバーの作り方に二つの型を挙げている[4]。フルサービスリゾルバーは、担当のサーバーを探し、サーバーの故障や通信の失敗に対処しながら、名前を最後まで引く。答えを覚えておくキャッシュを持ち、キャッシュの情報は時間が来たら消さなければならない。スタブリゾルバーは、近くの再帰的なサーバーに引く仕事を任せ、そのサーバーのキャッシュをほかの機器と分け合う[4]。

パソコンやスマホの中にあるのは、ふつうスタブリゾルバーで、頼む先は、家のルーターや通信事業者のリゾルバー、または 1.1.1.1 のような公開リゾルバーになる。RFC 9499 は、誰からの問い合わせでも受け付けるフルサービスリゾルバーをオープンリゾルバーと呼び、意図して開いているものは公開リゾルバー（public resolver）とも呼ばれる、と書いている[3]。

頼むときの約束は、問い合わせの RD（recursion desired）の印と、答えの RA（recursion available）の印で表す。RD は「最後まで引いてほしい」、RA は「このサーバーは再帰を引き受ける」という意味だ。再帰で答えるサーバーは、答えかエラーを返し、紹介は返さない。どのクライアントの再帰を引き受けるかは、サーバーが制限してよい[1]。

Linux の systemd-resolved は、説明書の上では、キャッシュを持つスタブリゾルバーだ。127.0.0.53 で問い合わせを受け、設定された DNS サーバー（ネットワークの設定で配られたものや、設定ファイルの DNS= に書いたもの）へ送る[5]。

キャッシュが空なら、ルートから一段ずつ下りる

フルサービスリゾルバーは、キャッシュに答えがなければ、根に近いサーバーから聞き、紹介をたどって担当の権威サーバーまで下りる。RFC 1034 の手順は、キャッシュを見る、聞くべきいちばんよいサーバーを探す、答えが来るまで問い合わせる、答えを読む、の四つだ[1]。

www.example.com の A レコード（IPv4 アドレス）を、キャッシュが空の状態で引く流れは次のようになる。リゾルバーはまず、根のサーバーのアドレスを知っている必要がある。多くのソフトは、根のサーバーの名前とアドレスの一覧（ルートヒント）を持っていて、そこから根のサーバーの今の一覧を得る。これをプライミングと呼ぶ[3]。根のサーバーに www.example.com を聞くと、根は答えを持たず、com の担当サーバーを紹介する。com のサーバーは、example.com の担当サーバーを紹介する。example.com の権威サーバーが AA の印を付けて A レコードを返し、リゾルバーはそれをキャッシュに入れて、スタブリゾルバーに返す[1][3]。

途中で受け取った紹介もキャッシュに入る[1]。RFC 1034 の手順は、聞く先を探すとき、名前そのもの、その親、さらにその親、と根の方向へ、手元にある NS レコードを探す[1]。そのため、次に別の .com の名前を引くときは、根を飛ばして com のサーバーから聞き始められる。

答えが CNAME（別名）だったときは、リゾルバーは CNAME をキャッシュに入れ、CNAME が指す名前に取り替えて、最初から引き直す[1]。

問い合わせは UDP と TCP の53番ポートで運ばれ、ふつうの問い合わせは UDP を先に使う[2][4]。答えが切り詰められていたら、TCP で聞き直す[4]。RFC 1034 は、答えを読むときは疑ってかかり、答えの ID が、送った問い合わせの ID と合うかを確かめるよう書いている[1]。

TTL は、答えを覚えておいてよい秒数

レコードには TTL が付いていて、リゾルバーはその秒数のあいだ、答えをキャッシュから返せる。RFC 1034 は、TTL を秒単位の数で、主にキャッシュに使い、捨てるまでにどれだけ覚えておいてよいかを表すとしている[1]。RFC 1035 は符号付きの32ビットの数と書いたが、RFC 2181 が、0 から 2,147,483,647（2の31乗引く1）までの符号なしの数と決め直した[2][6]。同じ名前・同じ種類のレコードの組（RRset）は、TTL をそろえなければならない[6]。

TTL が3600なら、リゾルバーは1時間のあいだ、権威サーバーに聞き直さずに答えられる。権威サーバーでアドレスを変えても、古い答えを覚えているリゾルバーの利用者には、TTL が切れるまで古いアドレスが返る。TTL を短くすれば切り替わりは早くなり、そのぶん権威サーバーへの問い合わせは増える。

「無い」という答えも覚えておける。名前が存在しない NXDOMAIN と、名前はあるが求めた種類のレコードがない NODATA を、否定の答えと呼ぶ[3]。RFC 2308 は、権威サーバーが否定の答えにゾーンの SOA レコードを付けることを求め、否定の答えを覚えておける時間を、SOA の MINIMUM 欄と SOA 自身の TTL の小さいほうで決める[7]。新しく作った名前が、作る前に一度引かれていると、この時間が過ぎるまで「無い」と返り続けることがある。

主なレコードは、種類ごとに入るものが違う

DNS は、名前にアドレスだけでなく、いくつもの種類のデータ（リソースレコード）を結びつける。種類は番号で区別され、主なものは RFC 1035 と、AAAA を定めた RFC 3596 にある[2][8]。

主なリソースレコード（RFC 1035・RFC 3596 から）
種類番号入るもの
A1IPv4 のアドレス（32ビット）
AAAA28IPv6 のアドレス（128ビット）
CNAME5別名が指す、正式な名前
MX15その名前あてのメールを受け取るサーバーの名前と、優先度の数
NS2そのゾーンを担当する権威サーバーの名前
TXT16文字列
PTR12別の名前を指す印。逆引きに使う

CNAME には決まりがある。CNAME を置いた名前には、ほかのデータを置かない。別名と正式な名前のデータが食い違わないようにするためで、こう決めておけば、キャッシュした CNAME を、ほかの種類について権威サーバーに確かめずに使える[1]。また、NS の値と MX の値には、別名（CNAME を持つ名前）を書いてはいけない[6]。

MX は、優先度の数が小さいほど先に使われる[2]。TXT の中身の意味は、置かれた場所で決まる[2]。たとえば、メールの送り元を確かめる SPF は、その名前からメールを送ってよいサーバーの一覧を、TXT レコードで公開する[9]。

逆引きは、アドレスを逆に並べた名前を引く

アドレスから名前を引く逆引きは、アドレスを名前に作り直して、その名前の PTR レコードを引く。IPv4 では、アドレスの四つの数を逆の順に並べ、in-addr.arpa を付ける。RFC 1035 の例では、10.2.0.52 のデータは 52.0.2.10.in-addr.arpa にある[2]。192.0.2.10 なら 10.2.0.192.in-addr.arpa だ。

逆に並べるのは、ネットワークの範囲ごとにゾーンを委任できるようにするためだ[2]。アドレスの上の桁が名前の右（根に近い側）に来るので、アドレスの範囲を持つ組織に、その範囲の逆引きのゾーンを任せられる。

IPv6 では、アドレスを16進数の1桁（4ビット）ずつ、下の桁から順に並べ、ip6.arpa を付ける[8]。2001:db8::1 なら、1.0.0.0 で始まる32桁の並びになり、最後は 8.b.d.0.1.0.0.2.ip6.arpa で終わる。

正引きのゾーン（example.com）と、逆引きのゾーン（in-addr.arpa の下）は、別々に委任される。ログに出た逆引きの名前は、そのアドレスの範囲を任された側が付けた名前で、その名前を正引きして同じアドレスが返るとは限らない。

リゾルバーに届かないと、名前が引けない

宛先への経路が生きていても、頼む先のリゾルバーに届かなければ、機器は名前を引けず、名前から始まる通信は始まらない。ルーティングの記事で見た2024年6月27日の事例では、1.1.1.1/32 の乗っ取りと 1.1.1.0/24 の経路の漏えいが重なり、一部の場所から 1.1.1.1 に届かなくなった[10]。Cloudflare は、世界の少数の利用者が、1.1.1.1 に届かない、または遅いと気づいたかもしれない、としている[10]。リゾルバーを 1.1.1.1 だけにしていた機器は、宛先のサーバーへの経路に問題がなくても、名前からアドレスを引く最初の段で止まる。

RFC 1123 は、スタブリゾルバーが、複数の再帰サーバーに問い合わせを向けられることを求めている[4]。Linux の resolv.conf には nameserver を3つまで書け、問い合わせが時間切れになると、次のサーバーに移る[11]。ただし、並べたリゾルバーがどれも同じ障害の影響を受ければ、並べても助けにならない。

守る側にとって、DNS の問い合わせのログは、どの機器がどの名前を引いたかを残す記録で、SIEM の記事でも取り込むログの一つに挙げた。リゾルバーや答えを偽られる話と、名前を乗っ取られる話は、DNS を守る記事で扱う。

自分の環境で確かめる

DNS の動きは、自分の機器の resolvectl と dig で観察できる。試すのは自分の機器と、自分が管理するネットワークの中だけにする。他人のサーバーに大量の問い合わせを送ったり、他人のゾーンの中身を丸ごと取ろうとしたりはしない。

resolvectl status は、いま使っている DNS の設定を、全体とリンクごとに見せる。resolvectl query example.com で名前を引くと、systemd-resolved を通した答えが出る。別の端末で resolvectl monitor を動かしておくと、手元の機器が出した問い合わせと答えが流れていく。これは機器の中の問い合わせで、キャッシュから答えたものも含む。resolvectl show-cache でキャッシュの中身を見られ、resolvectl flush-caches でキャッシュを消せる[5]。

dig は BIND に付いてくる道具で、サーバーを指定しなければ /etc/resolv.conf に書かれたサーバーに問い合わせる[12]。dig example.com の答えの flags に rd と ra があれば、再帰を頼み、サーバーが引き受けたことが分かる[1]。少し時間をおいてもう一度引き、答えの TTL を見比べると、キャッシュから答えたときの値の変わり方が分かる。

dig +trace example.com は、根のサーバーから紹介を自分でたどって問い合わせ、各段の答えを見せる[12]。dig +norecurse は RD の印を外して問い合わせ、dig -x にアドレスを渡すと、in-addr.arpa の名前を作って PTR を引く[12]。dig -x 192.168.1.1 のように家のルーターのプライベートアドレスで試すと、手元のリゾルバーが逆引きに何を返すかが分かる。
