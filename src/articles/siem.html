SIEM は、あちこちの機器に散らばったログを1か所に集め、形をそろえ、つなげて読み、怪しい動きを人に知らせる仕組みで、攻撃を止める役目は定義に入っていない。この記事は、その定義と、SIEM の中で起きる処理と、どのログから入れるかを、公的な手引きと製品の公式の資料で確かめたものだ。検知のルールと SOC（セキュリティの監視と対応をする部署）の仕事は次の記事、まわりの道具と学び方は3本目に書いた。

公的な定義は、集めることと、分析して示すことを含む

NIST・Gartner・オーストラリアの ACSC の三つの定義は、どれもログを集めることと、分析して人に示すことを含み、攻撃の遮断は含んでいない。

NIST の用語集は、SIEM のツールを「情報システムの構成要素からセキュリティのデータを集め、それを一つの画面で、行動につなげられる情報として示す機能を持つアプリケーション」と定義している。出どころは NIST の SP 800-128 だ[1]。

Gartner の用語集は、SIEM の市場を利用者の必要で定義している。イベントのデータをリアルタイムで分析して標的型の攻撃や侵害を早く見つけたい、そしてインシデント対応・フォレンジック（事後の調べ）・コンプライアンスのためにログを集め、保存し、調べ、報告したい、という必要だ。主なデータはログで、イベントのデータは、利用者・資産・脅威・脆弱性についての文脈と組み合わされる[2]。

2025年5月に ASD の ACSC（オーストラリアのサイバーセキュリティの機関）が CISA などと出した実務者向けの手引きでは、SIEM は、ネットワーク全体からログを集めて1か所にまとめ、セキュリティのために分析するソフトウェアまたは機器とされる。よく設定された SIEM は、ふだんのネットワークの動きの基準（ベースライン）と、ルールやフィルターを当てはめてログを分析し、つなげ、異常な動きに印を付ける[3]。

定義にあるのは、ベースラインとルールを当てはめた分析だ。ルールを書いて合わせる人と、結果を読む人がいなければ、SIEM はログを集めて貯めるだけの箱になる。

名前は、SIM と SEM を合わせたもの

SIEM は Security Information and Event Management の頭文字で、二つの製品の流れを合わせた言葉だとされる。一つは SIM（Security Information Management）で、ログを長く保存し、あとから分析して報告するほうに重心がある。もう一つは SEM（Security Event Management）で、イベントをリアルタイムで見張り、つなげて、知らせるほうに重心がある[4]。

この言葉は、2005年に Gartner のアナリスト、マーク・ニコレットとアムリット・ウィリアムズが使い始めたとされる[4]。確かめられたのは解説と二次資料までで、最初の文書は読めていない。

いまの SIEM は、リアルタイムの監視（SEM の側）と、過去にさかのぼる検索と分析（SIM の側）の両方を一つの製品で持っている。Gartner の定義も、その両方を挙げている[2]。

止めるのは、SOAR や別の機器と人

止める動きを受け持つのは、たとえば SOAR だ。同じ手引きは SOAR を、SIEM と同じようにログを集めて分析したうえで、あらかじめ決めた「プレイブック」（対応の手順書）を当てはめて対応を自動にする仕組みだと説明している。特定のイベントが起きたら、影響を受けた端末をネットワークから切り離す、といった動きだ[3]。

製品によっては、SIEM の画面から遮断まで動かせるものもある。無料のオープンソースの Wazuh の手引きには、総当たりのログインを見つけたときに、その送り元の IP アドレスを止める「Active Response」の設定が紹介されている[5]。これは製品が足した機能で、SIEM の定義の外にある。

経営層向けの手引きは、SIEM も SOAR も「入れたら終わり（set and forget）」の道具ではないと書く。入れて動かすことは、高い技能を持つ人を必要とする、手間のかかる、終わりのない作業だという[6]。SIEM が鳴らしたアラートを読み、本物かどうかを決め、次に何をするかを決めているのは、いまのところ人だ。

SIEM の中で起きる五つの処理

SIEM の中では、ログを集める・そろえる・つなげる・知らせる・残すの五つの処理が続いている。

集める

ログは、もともとばらばらの場所にある。ファイアウォールのログはファイアウォールの中に、Windows のログオンの記録はそれぞれのパソコンやサーバーの中に、クラウドの操作の記録はクラウドの管理の画面の中にある。攻撃は、入り込む、権限を手に入れる、ほかの端末へ移る、と段階を踏んで進むことがある。MITRE ATT&CK は、この段階を「戦術」として、偵察から影響まで並べている[7]。段階ごとに痕跡が残る場所は違うので、1か所だけを見ていても流れは見えにくい。

NIST の SP 800-92（2006年）は、ログの管理を、ログを作る・送る・保存する・分析する・捨てる、という一続きの流れとして扱い、ログを1か所に集める基盤をつくることを勧めている[8]。SIEM は、この基盤の上に立つ代表的な道具だ。

集め方には、見張る機器に小さなプログラム（エージェント）を入れて送らせる方法と、機器が自分で送り出すログ（syslog など）を受け取る方法がある。Wazuh の場合、パソコンやサーバーにはエージェントを入れ、エージェントを入れられないファイアウォール・スイッチ・ルーターなどからは syslog を受け取る[9]。

そろえる

同じ出来事でも、機器ごとにログの書き方が違うので、SIEM は項目を共通の形に当てはめ直す。ファイアウォールのログ、Windows のログオンのイベント、Web サーバーのアクセスログは、どれもネットワークの動きを表しているのに、項目の名前も並びも違う。Wazuh は、それぞれのログを読み解いて、送り元の IP アドレス・宛先の IP アドレス・ユーザー名・プロセス・イベントの種類といった共通の項目に当てはめ直す。同じ検索やルールを、ログの出どころを気にせずに使えるようにするためだ[10]。

これを正規化（ノーマライゼーション）と呼ぶ。Elastic Security は ECS（Elastic Common Schema）という共通の項目の決まりを使い、ほかの道具で集めたデータも ECS に合わせることを求めている[11]。ECS では、送り元の IP アドレスは source.ip、ユーザー名は user.name、出来事の結果は event.outcome に入れ、event.outcome の値は failure・success・unknown の三つに決まっている[12]。Elastic が公開している SSH の総当たりの検知ルールも、この項目の名前で「同じ端末・送り元・ユーザー名で、event.outcome が failure の認証が続いたあとに success が来る」と書かれている[13]。正規化が雑で、片方のログでは「user」、もう片方では「account_name」とユーザー名が書かれたままなら、ルールは二つを同じ人だと分からない。

つなげる

相関分析は、別々のログを、時間・ユーザー・端末・IP アドレスといった共通の手がかりでつなげて読むことだ。ログイン失敗の1件は、パスワードを打ち間違えた人の記録かもしれない。同じ送り元から数分のうちに何十件も失敗が続き、その直後に成功があれば、推測が当たった可能性が出てくる。1件ずつでは普通の出来事が、並べると一つの筋になる。ルールの具体的な形は次の記事に書いた。

Gartner の定義にあった「文脈との組み合わせ」も、つなげる処理の一つだ[2]。同じログイン失敗でも、相手がふつうの社員のアカウントか管理者のアカウントか、重要なデータのあるサーバーか試験用の端末かで、重さは変わる。資産の一覧や利用者の情報を SIEM が持っていれば、アラートにその文脈を添えられる。

知らせる

ルールの条件に合うと、SIEM はアラートを出す。アラートには重さ（重大度）が付き、担当者の画面に並ぶ。製品の多くには、関係するアラートをまとめて一つの事案として扱う画面や、関係するログをさかのぼって検索する画面がある。Splunk Enterprise Security の説明では、事案の管理と、アラートのトリアージ（ふるい分け）・調査・対応が、一つの流れとしてつながっている[14]。

残す

SIEM は、アラートを出したあともログを残す。侵入に気づくのが、侵入からしばらくたってからのこともあるからだ。あとから「あの日、このアカウントは何をしていたか」をさかのぼれるかは、どれだけの期間、どの形で残しているかで決まる。何日分を残すかは、法律や業界の決まり、組織の方針で変わり、一つの正解はない。ダッシュボードやコンプライアンスの報告も、この保存されたデータから作られる[2]。

どのログから入れるかは、共同の手引きが順を付けている

2025年5月の共同の手引き「Priority logs for SIEM ingestion」は、SIEM に入れるログの源を、おおよそ優先の高い順に並べている。最初が EDR（端末での検知と対応の道具）のログで、ネットワーク機器のログ、Microsoft のドメインコントローラーのログ、Active Directory などのディレクトリーのセキュリティのログ、Windows の端末のログと続く。そのあとに、仮想化の基盤、制御システム（OT）、クラウド、コンテナ、データベースなどが続く[15]。

手引きは、この順番を、ふつうの企業のネットワークで始めるための出発点だとしている。新しく SIEM を入れるときは、優先の高いものから先に入れ、それぞれの取り込みが正しく続いているかを定期的に確かめることを勧めている[15]。

ログの種類ごとに、分かることが違う。下の表は僕の整理で、例のアドレスは文書のために取ってある 192.0.2.0/24・198.51.100.0/24・example.com を使った。

ログの種類と、分かること
ログ主に分かること見つけたい動きの例
ファイアウォールどこからどこへ、どのポートで通信し、通したか止めたか社内の端末 192.0.2.15 が、ふだん通信しない外の宛先 198.51.100.7 へ、夜中に通信している
Web プロキシ社内の端末が、どの URL やドメインへ、どれだけのデータを送り、受け取ったかある端末だけが、見慣れないドメインへ大きなデータを送っている
DNSどの端末が、どのドメイン名を問い合わせたかexample.com の下に、意味の読めない長い名前の問い合わせが続いている
認証（ログオン）誰が、いつ、どこから、成功したか失敗したか同じアカウントへの失敗が続いたあとに、成功している
端末（EDR・OS）どのプログラムが、どの親のプログラムから起動し、何をしたか文書を開くソフトから、コマンドの実行が始まっている
クラウド誰が、どの設定を変え、どの権限やアカウントを作ったかふだん使わない場所から、管理者の権限が作られている

Windows の認証のログでは、イベントの番号（イベント ID）が手がかりになる。JPCERT/CC が公開している調査の道具 LogonTracer の説明には、ログオンの成功が 4624、失敗が 4625、ユーザーのアカウントが作られたのが 4720、セキュリティのグループにメンバーが足されたのが 4728・4732・4756、NTLM の認証が 4776、Kerberos の認証が 4768・4769、と並んでいる[16]。SIEM のルールの多くは、こうした番号の組み合わせで書かれている。

ログは、多く集めればよいわけではない

ログは、多く入れるほど見えるわけではなく、答えたいことに必要なログが入っているかで見えるものが決まる。同じ手引きは、ファイアウォールや DNS のログはとても量が多く、その量が、中に含まれる情報の大切さを覆い隠してしまうことがある、と書いている[15]。量の多いログを全部入れれば、検索は重くなり、ルールの雑音も増える。経営層向けの手引きによると、SIEM の料金は取り込むデータの量で決まる仕組みが多く、取り込みを管理しないと、払いすぎる危険もある[6]。

2024年8月に ASD の ACSC が中心になり、CISA・FBI・NSA などが加わって出した「Best practices for event logging and threat detection」は、組織として承認したログの方針を持つことを、四つの柱の最初に置いている。残りの三つは、ログを1か所で見て相関できること、ログを安全に保存して改ざんされていないと言えること、自分たちに関係のある脅威に合わせた検知の戦略を持つことだ[17]。何を、なぜ集めるかを先に決める順番になっている。

少なすぎても見えない。同じ2024年の手引きは、OS に元からある正規の道具を悪用して目立たずに動く「環境寄生型（living off the land）」の手口を事例として取り上げている[17]。正規の道具の動きは、1件ずつ見ればふつうの操作と区別しにくい。ふだんの動きと比べて違いを見つけるには、ふだんの動きが分かるだけの記録が、前もって残っている必要がある。

SIEM が画面に出すのは、集めたログの中から、ルールが拾い上げたものだけだ。入っていないログの中で起きたことは、画面には出てこない。
