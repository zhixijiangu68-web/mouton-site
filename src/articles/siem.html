SIEM を入れても、それだけでは攻撃は止まらない。SIEM がしているのは、あちこちの機器に散らばったログを1か所に集め、形をそろえ、つなげて読み、怪しい動きを人に知らせるところまでだ。止めるかどうか、どう止めるかは、多くの場合、別の仕組みと人が決めている。

SOC（セキュリティの監視と対応をする部署）の仕事を学び始めると、早いうちに SIEM という言葉に出会う。けれど、何をする道具なのかを一文で言おうとすると、意外にむずかしい。「ログを集める箱」と言われることもあれば、「入れれば守れる」と受け取られることもある。どちらも半分だけ当たっていて、半分は外れている。

この記事は、SOC アナリストを目指して勉強している僕が、SIEM について公的な手引きと製品の公式の資料で確かめたことをまとめたものだ。米国の NIST、オーストラリアの ASD と米国の CISA が中心になった共同の手引き、MITRE ATT&CK、そして Wazuh・Elastic・Splunk・Microsoft・IBM の公式の資料を読んだ。製品は名前と種類だけを書き、比べて勧めることはしない。

検知のルールの例は出すが、攻撃の手順は書かない。ルールが何を見ているのか、なぜその形なのかまでを扱う。例に出す IP アドレスやドメインは、文書のために取ってある 192.0.2.0/24 や 198.51.100.0/24、example.com を使う。

よく言われることの判定

確かさは、資料が公的な手引きか、公式の説明か、調査か、予測かと、資料の数から付けた目安。

{% verdictTable claims %}

SIEM は、ログを集めて、つなげて、人に知らせる仕組みだ

公的な定義は、どれも「集める」と「分析して示す」を含んでいる

NIST の用語集は、SIEM のツールを「情報システムの構成要素からセキュリティのデータを集め、それを一つの画面で、行動につなげられる情報として示す機能を持つアプリケーション」と定義している。出どころは NIST の SP 800-128 だ[1]。

Gartner の用語集は、もう少し踏み込んでいる。SIEM の市場を、イベントのデータをリアルタイムで分析して標的型の攻撃や侵害を早く見つけたい、そしてインシデント対応・フォレンジック（事後の調べ）・コンプライアンスのためにログを集め、保存し、調べ、報告したい、という利用者の必要で定義している。主なデータはログで、イベントのデータは、利用者・資産・脅威・脆弱性についての文脈と組み合わされる[2]。

2025年5月に ASD の ACSC（オーストラリアのサイバーセキュリティの機関）が CISA などと出した実務者向けの手引きでは、SIEM は、ネットワーク全体からログを集めて1か所にまとめ、セキュリティのために分析するソフトウェアまたは機器とされる。よく設定された SIEM は、ふだんのネットワークの動きの基準（ベースライン）と、ルールやフィルターを当てはめてログを分析し、つなげ、異常な動きに印を付ける[3]。

三つの定義に共通するのは、集めることと、分析して人に示すことだ。逆に、どの定義にも「攻撃を遮断する」は入っていない。

名前は、SIM と SEM を合わせたものだった

SIEM は Security Information and Event Management の頭文字で、二つの製品の流れを合わせた言葉だとされる。一つは SIM（Security Information Management）で、ログを長く保存し、あとから分析して報告するほうに重心がある。もう一つは SEM（Security Event Management）で、イベントをリアルタイムで見張り、つなげて、知らせるほうに重心がある[4]。

SIEM という言葉は、2005年に Gartner のアナリスト、マーク・ニコレットとアムリット・ウィリアムズが使い始めたとされる[4]。ただ、僕が確かめられたのは、これを伝える解説と二次資料までで、最初の文書そのものは読めていない。名前の由来は、その程度の確かさの話として置いておく。

いまの SIEM は、二つの役目を一つの製品で持っている。リアルタイムの監視（SEM の側）と、過去にさかのぼる検索と分析（SIM の側）だ。Gartner の定義も、リアルタイムのイベントの分析と、過去のデータへの問い合わせや長い期間の分析の両方を挙げている[2]。

止めるのは、別の仕組みと人のほうにある

止める動きを受け持つのは、たとえば SOAR だ。同じ手引きは SOAR を、SIEM と同じようにログを集めて分析したうえで、あらかじめ決めた「プレイブック」（対応の手順書）を当てはめて対応を自動にする仕組みだと説明している。特定のイベントが起きたら、影響を受けた端末をネットワークから切り離す、といった動きだ[3]。

製品によっては、SIEM の画面から遮断まで動かせるものもある。無料のオープンソースの Wazuh の手引きには、総当たりのログインを見つけたときに、その送り元の IP アドレスを止める「Active Response」の設定が紹介されている[5]。ただ、これは SIEM の定義の外にある機能で、Wazuh 自身も、自分を XDR と SIEM の機能を一つにした基盤だと説明している[6]。

経営層向けの手引きは、SIEM も SOAR も「入れたら終わり（set and forget）」の道具ではないと書く。入れて動かすことは、高い技能を持つ人を必要とする、手間のかかる、終わりのない作業だという[7]。SIEM が鳴らしたアラートを読み、本物かどうかを決め、次に何をするかを決めているのは、いまのところ人だ。

SIEM の中では、集める・そろえる・つなげる・知らせる・残すが起きている

集める：ログは、もともとばらばらの場所にある

ファイアウォールのログはファイアウォールの中に、Windows のログオンの記録はそれぞれのパソコンやサーバーの中に、クラウドの操作の記録はクラウドの管理の画面の中にある。攻撃は、入り込む、権限を手に入れる、ほかの端末へ移る、と段階を踏んで進むことがある。MITRE ATT&CK は、この段階を「戦術」として、偵察から影響まで並べている[8]。段階ごとに痕跡が残る場所は違うので、1か所だけを見ていても、流れは見えにくい。

NIST の SP 800-92（2006年）は、ログの管理を、ログを作る・送る・保存する・分析する・捨てる、という一続きの流れとして扱い、ログを1か所に集める基盤をつくることを勧めている[9]。SIEM は、この「1か所に集める」の上に立つ代表的な道具だ。

集め方には、見張る機器に小さなプログラム（エージェント）を入れて送らせる方法と、機器が自分で送り出すログ（syslog など）を受け取る方法がある。Wazuh の場合、パソコンやサーバーにはエージェントを入れ、エージェントを入れられないファイアウォール・スイッチ・ルーターなどからは syslog を受け取る[6]。

そろえる：同じ出来事でも、機器ごとに書き方が違う

集めただけのログは、そのままではつなげて読めない。この点は、Wazuh の説明がいちばん分かりやすかった。ファイアウォールのログ、Windows のログオンのイベント、Web サーバーのアクセスログは、どれもネットワークの動きを表しているのに、項目の名前も並びも違う。そこで Wazuh は、それぞれのログを読み解いて、送り元の IP アドレス・宛先の IP アドレス・ユーザー名・プロセス・イベントの種類といった共通の項目に当てはめ直す。同じ検索やルールを、ログの出どころを気にせずに使えるようにするためだ[10]。

これが正規化（ノーマライゼーション）だ。Elastic Security は ECS（Elastic Common Schema）という共通の項目の決まりを使い、ほかの道具で集めたデータも ECS に合わせることを求めている[11]。正規化が雑だと、片方のログでは「user」、もう片方では「account_name」と書かれたユーザー名を、ルールが同じ人だと分からない。SIEM の質は、地味なこの段階にかなり左右される、と僕は読んでいる。

つなげる：1件では普通でも、並べると怪しいものがある

相関分析は、別々のログを、時間・ユーザー・端末・IP アドレスといった共通の手がかりでつなげて読むことだ。ログイン失敗の1件は、パスワードを打ち間違えた人の記録かもしれない。同じ送り元から数分のうちに何十件も失敗が続き、その直後に成功があれば、話が変わる。1件ずつでは普通の出来事が、並べると一つの筋になる。具体的なルールの形は、あとの節で見る。

Gartner の定義にあった「文脈との組み合わせ」も、つなげる仕事の一つだ[2]。同じログイン失敗でも、相手がふつうの社員のアカウントか、管理者のアカウントか、重要なデータのあるサーバーか、試験用の端末かで、重さは変わる。資産の一覧や利用者の情報を SIEM が持っていれば、アラートにその文脈を添えられる。

知らせる：アラートと、調べるための画面

ルールの条件に合うと、SIEM はアラートを出す。アラートには重さ（重大度）が付き、担当者の画面に並ぶ。製品の多くには、関係するアラートをまとめて一つの事案として扱う画面や、関係するログをさかのぼって検索する画面がある。Splunk Enterprise Security の説明では、事案の管理と、アラートのトリアージ（ふるい分け）・調査・対応が、一つの流れとしてつながっている[12]。

残す：あとから調べるために、ログを保存する

SIEM は、アラートを出したあとも、ログを残しておく。侵入に気づくのが、侵入からしばらくたってからのこともあるからだ。あとから「あの日、このアカウントは何をしていたか」をさかのぼれるかは、どれだけの期間、どの形で残しているかで決まる。何日分を残すかは、法律や業界の決まり、組織の方針で変わり、一つの正解はない。

ダッシュボードやレポートも、この保存されたデータから作られる。Gartner の定義が挙げるように、ネットワークの監視、利用者の動きの監視、コンプライアンスの報告にも、同じデータが使われる[2]。

どのログを入れるかで、見えるものが決まる

共同の手引きは、ログの源に優先の順を付けている

2025年5月の共同の手引き「Priority logs for SIEM ingestion」は、SIEM に入れるログの源を、おおよそ優先の高い順に並べている。最初が EDR（端末での検知と対応の道具）のログで、ネットワーク機器のログ、Microsoft のドメインコントローラーのログ、Active Directory などのディレクトリーのセキュリティのログ、Windows の端末のログと続く。そのあとに、仮想化の基盤、制御システム（OT）、クラウド、コンテナ、データベース、モバイル端末の管理、Windows の DNS サーバー、Linux の端末、macOS の端末が並ぶ[13]。

手引きは、この順番を、ふつうの企業のネットワークで始めるための出発点だとしている。新しく SIEM を入れるときは、優先の高いものから先に入れ、それぞれの取り込みが正しく続いているかを、定期的に確かめることを勧めている[13]。

ログの種類ごとに、答えられる問いが違う

ログの種類は、それぞれ違う問いに答える。勉強のために、僕は次のように整理している。例のアドレスはすべて文書用のものだ。

ログの種類と、答えられる問いの例
ログ主に分かること問いの例
ファイアウォールどこからどこへ、どのポートで通信し、通したか止めたか社内の端末 192.0.2.15 が、ふだん話さない外の宛先 198.51.100.7 へ、夜中に通信していないか
Web プロキシ社内の端末が、どの URL やドメインへ、どれだけのデータを送り、受け取ったかある端末だけが、見慣れないドメインへ大きなデータを送っていないか
DNSどの端末が、どのドメイン名を問い合わせたかexample.com の下に、意味の読めない長い名前の問い合わせが続いていないか
認証（ログオン）誰が、いつ、どこから、成功したか失敗したか同じアカウントへの失敗が続いたあとに、成功していないか
端末（EDR・OS）どのプログラムが、どの親のプログラムから起動し、何をしたか文書を開くソフトから、コマンドの実行が始まっていないか
クラウド誰が、どの設定を変え、どの権限やアカウントを作ったかふだん使わない場所から、管理者の権限が作られていないか

Windows の認証のログでは、イベントの番号（イベント ID）が手がかりになる。JPCERT/CC が公開している調査の道具 LogonTracer の説明には、ログオンの成功が 4624、失敗が 4625、ユーザーのアカウントが作られたのが 4720、セキュリティのグループにメンバーが足されたのが 4728・4732・4756、NTLM の認証が 4776、Kerberos の認証が 4768・4769、と並んでいる[14]。SIEM のルールの多くは、こうした番号の組み合わせで書かれている。

多く集めれば、よく見えるわけではない

ログは多いほど安心に思える。けれど同じ手引きは、ファイアウォールや DNS のログはとても量が多く、その量が、中に含まれる情報の大切さを覆い隠してしまうことがある、と書いている[13]。量の多いログを全部入れれば、検索は重くなり、ルールの雑音も増える。

お金の面もある。経営層向けの手引きによると、SIEM の料金は取り込むデータの量で決まる仕組みが多く、取り込みを管理しないと、払いすぎる危険がある[7]。

2024年8月に ASD の ACSC が中心になり、CISA・FBI・NSA などが加わって出した「Best practices for event logging and threat detection」は、組織として承認したログの方針を持つことを、四つの柱の最初に置いている。残りの三つは、ログを1か所で見て相関できること、ログを安全に保存して改ざんされていないと言えること、自分たちに関係のある脅威に合わせた検知の戦略を持つことだ[15]。何を、なぜ集めるかを先に決めておく、という順番になっている。

逆に、少なすぎても見えない。同じ2024年の手引きは、OS に元からある正規の道具を悪用して目立たずに動く「環境寄生型（living off the land）」の手口を事例として取り上げている[15]。正規の道具の動きは、1件ずつ見ればふつうの操作と区別しにくい。ふだんの動きと比べて違いを見つけるには、ふだんの動きが分かるだけの記録が、前もって残っている必要がある。量の問題は「多いか少ないか」ではなく、「その問いに答えるログが入っているか」なのだと、僕は読んだ。

「ログイン失敗が続いたあとの成功」を、ルールはこう見ている

MITRE ATT&CK の検知の例は、失敗と成功を組み合わせている

相関ルールの例として、いちばんよく挙がるのが総当たり（ブルートフォース）だ。ATT&CK では「Brute Force」（T1110）という技術にあたり、パスワードが分からないときに、繰り返し推測してアカウントに入ろうとする手口とされる[16]。

ATT&CK は、技術ごとに「検知の戦略」と「分析」の例を載せている。総当たりの検知の戦略（DET0463）には、Windows での分析の例として、大量のログオンの失敗のあとに、怪しい利用者・端末・時間帯からの成功が続くことを見るものがある。使うログは Windows のセキュリティのログで、イベント ID の 4625 と 4776 を挙げている。Linux では、同じ IP アドレスや利用者で認証の失敗が続いたあとの成功を、auditd の記録で見る例がある[16]。

大事なのは、失敗の回数だけを見ていないことだ。失敗が続くだけなら、推測が外れ続けているか、誰かがパスワードを忘れているだけかもしれない。失敗のあとに成功があると、推測が当たった可能性が出てくる。1件ずつのログでは分からないことが、順番をつなげると見えてくる。これが相関分析の考え方だと思う。

三つのルールを並べると、時間の幅も回数も違っていた

出どころ何をつなげるか時間の幅失敗の数
MITRE ATT&CK（DET0463 の Windows の例）ログオンの失敗のあとの成功環境に合わせて変える（例として5〜10分）環境に合わせて変える（例として10〜15回）
Wazuh のルール 40112同じ送り元の IP アドレスで、「認証の失敗が続いた」のアラートのあとの成功240秒前のアラートの条件による（ルール 40111 は160秒に12回、SSH のルール 5763 は120秒に8回）
Elastic「Potential Successful SSH Brute Force Attack」同じ端末・送り元の IP アドレス・ユーザー名で、SSH の失敗のあとの成功15秒25回

表のもとは、ATT&CK の公開のデータ[16]、Wazuh の 4.14.0 の版のルールのファイル[17]、Elastic の公開の検知ルール[18]だ。Wazuh のルール 40112 は、重さが12で、ATT&CK の T1078（正規のアカウントの悪用）と T1110 の番号が付いている[17]。

同じ考え方のルールでも、時間の幅は15秒から数分まで、失敗の数は8回から25回まで開いている。どれが正しいという話ではない。ATT&CK は、時間の幅、見張る利用者の範囲、アラートを出すまでの失敗の数を、環境に合わせて変える項目としてはっきり書いている[16]。ルールは、置かれる場所に合わせて形を変える前提で作られている。

パスワードスプレーは、アカウントをまたいで数えないと見えない

回数で見るルールには、すり抜ける形もある。ATT&CK の「Password Spraying」（T1110.003）は、よく使われるパスワードを一つか少しだけ用意し、それを多くの違うアカウントに試す手口だ。一つのアカウントに何度も失敗するとロックがかかるので、それを避けるためだとされる[19]。

この場合、一つのアカウントあたりの失敗は1回か2回しかない。アカウントごとに数えるルールでは、しきい値に届かない。ATT&CK の検知の例は、決めた時間の幅（例として10分）の中で、多くの違うアカウントにわたって認証の失敗が出ていることを見る。調整する項目も、いくつのアカウントにわたったらアラートを出すかや、利用者全体のうち失敗したアカウントの割合になっている[19]。数える単位を、一つのアカウントから、送り元や時間の幅に移しているわけだ。

総当たりのルールを一つ持っているから、パスワードを当てようとする手口はすべて見える、とは言えない。手口の形が変われば、数える単位も変える必要がある。

ログインのほかにも、つなげて見る例がある

相関は、ログインだけの話ではない。ATT&CK には、ほかにもログをつなげて見る検知の例が並んでいる。

一つは、端末の中にローカルのアカウントが作られたこと（T1136.001）だ。Windows では、アカウントが作られたイベント（4720）が、PowerShell や net.exe のようなプログラムの起動の直後に起きていないかを見る。プログラムの起動とアカウントの作成のあいだの時間の幅（例として5秒〜2分）や、どの権限で動いたかを、調整する項目にしている[20]。

もう一つは、イベントログが消されたこと（Clear Windows Event Logs）だ。Windows のセキュリティのログに残るイベント 1102 と、ログを消すプログラムの起動や、ログのファイルの削除の記録を、ひと続きの動きとして見る[21]。痕跡を消す動きそのものが、痕跡になる。消される前に SIEM へ送ってあれば、記録は SIEM の側に残る。ログを1か所に集めることには、こういう意味もある。

ルールを、製品に頼らない形で書く取り組みもある

ルールの書き方は、製品ごとに違う。そこで、ルールを製品に頼らない形で書く「Sigma」という取り組みがある。Sigma は、ログの中の出来事を書き表すための、汎用でオープンなシグネチャの形式で、公開のリポジトリには3,000を超える検知ルールがある。ルールは、それぞれの SIEM の問い合わせの言葉に変換して使う[22]。一つのルールを読めば、どの製品でも同じ考え方が使えるので、勉強の材料としても読みやすい。

ルールは、入れたときが始まりだった

調整と雑音の削減は、終わりのない作業とされている

製品には、最初から多くの検知ルールが入っている。Elastic の手引きは、検知の仕組みを育てる流れを七つの段階で示し、Elastic が保守しているルールの一式を有効にするのを3番目に置いている。その前に、要件を確かめる段階と、どの脅威が自分の環境にとって大事かを決め、ATT&CK で足りないところを探す段階がある。そして、調整と雑音の削減は、最後の段階ではなく、ずっと続くものだと書いている[23]。

直し方も分かれている。ルールそのものが広すぎて、どの環境でもふつうの動きに反応するなら、問い合わせやしきい値を変える（調整）。ルールは正しいが、自分の環境に特有の安全な動きに反応するなら、例外を足す。Elastic の手引きは、社内で作ったアプリケーションが、怪しいプログラムの動きを見るルールに反応してしまう例を挙げ、そのアプリケーションの名前を例外に足すやり方を示している[23]。

ATT&CK の検知の例が、しきい値や時間の幅を「変える項目」として書いていたのも、同じ考え方だと思う[16]。ルールは、置かれる環境のふだんの姿を知らないまま作られている。ふだんの姿を教えるのは、運用する人だ。

どの種類のルールを使うかで、見えるものが変わる

Elastic のルールの種類の説明を読むと、検知の考え方の幅が分かる。決まった値や条件に合うものを探すルール、数がしきい値を超えたら出すルール（総当たりのような量の手口に向くとされる）、出来事の順番や「あるはずの出来事がない」ことを見るルール（EQL）、脅威の情報と照らし合わせるルール、初めて現れた値に反応するルール、機械学習でふだんの動きを学び、外れたものを出すルールがある[24]。

先ほどの Elastic の SSH のルールは、順番を見る EQL で書かれていた[18]。失敗の回数だけを見るなら、しきい値のルールで足りる。失敗のあとに成功が来た、という順番を見るには、順番を表せるルールが要る。どの種類を選ぶかは、何を問いたいかで決まる。

SOC アナリストは、SIEM のアラートから仕事を始める

トリアージで、本物か、急ぐか、誰に渡すかを決める

SOC のアナリストの仕事は、SIEM の画面に並んだアラートを見るところから始まることが多い。最初にするのがトリアージ（ふるい分け）で、Splunk Enterprise Security の説明でも、調査と対応の前に置かれている[12]。このアラートは本当に怪しい動きを示しているのか、どれくらい急ぐのか、自分で調べるのか、次の担当に渡すのかを決める。

本物らしいと判断したら、調査に進む。アラートの前後の時間に、同じユーザー・同じ端末・同じ IP アドレスで何が起きていたかを、SIEM の検索でさかのぼる。ログインに成功したあと、そのアカウントは何をしたか。ほかの端末にも、同じ送り元から失敗が出ていないか。ここで、最初に集めて正規化しておいたログが生きてくる。

NIST が2025年4月に出した SP 800-61 の第3版は、インシデント対応を、組織のセキュリティの仕事全体の中に組み込んで考える形に改めた。土台にしているのは CSF 2.0 の六つの機能（統治・識別・防御・検知・対応・復旧）で、どの機能もインシデント対応に関わるとしている[25]。SIEM のアラートは、その中の検知から対応への入口にあたる。

「誤検知」の多くは、正しく鳴ったが害のない動きだった

アラートの中には、調べてみると問題のないものが多い。オックスフォード大学のアラーマディらは、SOC で働く実務者への調査と聞き取りをもとに、2022年の USENIX Security で「99% False Positives」という題の研究を発表した[26]。

この研究が示したのは、実務者が「誤検知」と呼んでいるものの多くが、厳密には誤りではない、ということだった。ルールの通りに正しく鳴ったが、その組織の環境では正当な動きだったもので、著者たちはこれを「benign trigger（害のない引き金）」と呼んでいる[26]。僕なりの例を挙げると、管理者が障害の対応で夜中にサーバーへ入った記録は、ルールから見れば怪しく、組織から見れば仕事の一部だ。

この違いは、直し方に関わる。ルールが間違っているなら、ルールを直す。ルールは正しいが環境の文脈を知らないなら、文脈を足す。例外を足す、資産や利用者の情報と組み合わせる、といったやり方だ。著者たちは、アラートが持つとよい性質として、信頼できる・説明できる・分析に役立つ・文脈を持つ・ほかへ移せる、の五つを提案している[26]。

アラート疲れは、量と質の両方の問題だった

アラートが多すぎると、一つひとつを丁寧に見られなくなる。アラート疲れ（alert fatigue）と呼ばれる状態だ。同じ研究は、すぐに反応でき、解釈できて意味のあるアラートを出す道具が、アラートによる燃え尽きを減らすことにつながる、と結んでいる[26]。

アラート疲れや誤検知の割合については、さまざまな数字が出回っている。ただ、僕が見た範囲では、調べ方がはっきりしない調査が多かったので、この記事では割合を使わない。言えるのは、アラートの数を減らすことと、一つひとつのアラートに文脈を持たせることは、別々の手当てだということだ。数を減らしても、残ったアラートが読み解けなければ、アナリストの手間は大きくは減らない。

AI は、アナリストの席を空けたのか

SIEM や、その周りの道具には、機械学習や生成 AI の機能が足されてきている。Elastic のルールの種類には、機械学習でふだんの動きからの外れを見つけるものがあり[24]、JPCERT/CC の LogonTracer も、2.0 の版で OpenAI の GPT のモデルを使った分析の機能を入れた[14]。

では、AI があれば SOC のアナリストは要らなくなるのか。公的な手引きは、そうは書いていない。2025年の実務者向けの手引きは、SIEM と SOAR が役に立つには、技能を持つ人による監視と、定期的な試験と、改善の繰り返しが要るとしている[3]。経営層向けの手引きも、費用の中に、専門の技能を持つ人を雇い、とどめ、育てる費用を入れている[7]。

Gartner は2024年12月に、「Predict 2025: There Will Never Be an Autonomous SOC（自律した SOC は、これからもできない）」という題の予測を出している[27]。僕が読めたのは要旨の冒頭だけで、理由の詳しいところは確かめられていない。予測は予測で、長い期間のデータではない。

いまの資料から僕が読めるのは、AI が人の席をなくすというより、人がする仕事の中身が変わっていく、という見通しまでだ。何を自動に任せ、どこで人が判断するかを決めること自体が、仕事の一部になっていく。この先どうなるかは、まだ確かめられていない。

SOAR・EDR・XDR・ログ管理と、どこが違うのか

セキュリティの道具は略語が多い。違いを、何を見て、何をするかで並べてみた。

似た名前の道具の違い（僕の整理）
名前主に見るもの主にすること
ログ管理あらゆるログ集めて、保存し、検索できるようにする
SIEM多くの機器の、セキュリティにかかわるログ形をそろえ、つなげて分析し、アラートを出し、保存する
SOARSIEM のアラートや、ログプレイブックに沿って、対応を自動にする（端末の切り離しなど）
EDRパソコンやサーバーの中の動き端末で怪しい動きを見つけ、その端末で対応する
XDR端末に加えて、ネットワーク・メール・クラウドなどいくつもの領域の検知と対応を一つにまとめる（範囲は製品ごとに違う）

ログ管理と SIEM の境目は、セキュリティのための分析をするかどうかにある。NIST の SP 800-92 が扱うのは、ログの管理全体の基盤づくりで[9]、SIEM はその上で、セキュリティのための分析とアラートを受け持つ。

SOAR は、SIEM の隣に置かれることが多い。実務者向けの手引きによると、SOAR の中には、自分でログを集めて分析するものもあれば、すでにある SIEM とつないで、その機能を使うものもある[3]。

EDR は、端末の中を深く見る道具だ。共同の手引きは、SIEM に入れるログの優先の最初に、EDR のログを置いていた[13]。ここで EDR と SIEM は取って代わる関係ではなく、EDR が SIEM にログを渡す関係として描かれている。

XDR は、端末の外まで検知と対応を広げる考え方だ。僕が読んだ範囲では、どこまでを XDR と呼ぶかは製品ごとに違い、一つの定義にまとまっていなかった。製品の側でも、境目は重なっている。Wazuh は自分を XDR と SIEM の機能を一つにした基盤だと説明し[6]、Microsoft Sentinel は、クラウドで動く SIEM で、SOAR の機能も持つと説明している[28]。「SIEM は XDR に置き換わった」と言えるだけの調査は、僕が探した範囲の公的な資料には見つからなかった。

主な製品は、提供のしかたと土台で分かれる

SIEM の製品は多い。ここでは、勉強の中でよく名前を見るものを、公式の説明に書かれた種類だけ並べる。比べて勧めることはしない。どれが合うかは、組織の環境と、すでに使っている道具で変わる。

提供のしかたで見ると、クラウドのサービスとして使うものと、自分のサーバーやプライベートクラウドに入れて動かすものがある。Gartner も、SIEM は SaaS として、または利用者の側のオンプレミスやプライベートクラウドで提供される、と書いている[2]。

入れたあとに難しいのは、お金とデータと人だった

費用は、取り込む量で増えやすい

経営層向けの手引きは、SIEM と SOAR の費用として、製品の料金のほかに、人の費用を挙げている。専門の技能を持つ人を雇ってとどめる費用、いまいる人の技能を上げる費用と続けての訓練、外に任せるならその委託料だ。料金はデータの取り込みの量で決まる仕組みが多く、取り込みを管理しないと払いすぎる危険がある、とも書いている[7]。

一方で手引きは、適切に入れて動かす費用より、サイバーのインシデントが起きたときの費用のほうが、はるかに大きくなりうるとも書いている[7]。費用がかかるから何もしない、という読み方は、手引きの書き方とは違う。

データは、集めるより、正しく入り続けるほうが難しい

ログの取り込みは、一度つないだら終わりではない。機器の更新でログの形が変わる、エージェントが止まる、送り先の設定が消える。そうなっても、SIEM の画面には「何も起きていない」ように見える。アラートがないことと、何も起きていないことは違う。共同の手引きが、取り込みが正しく続いているかを定期的に確かめるよう勧めていた[13]のは、このためだと僕は読んでいる。

ルールを合わせる人は、組織の外から買ってきにくい

ルールを調整するには、その組織のふだんの姿を知っている必要がある。誰が夜中にサーバーへ入るのか、どのアプリケーションが変わった動きをするのか。製品の標準のルールは出発点で、組織に合わせる作業は、組織のことを知る誰かがすることになる。手引きが「入れたら終わり」ではないと書き、技能を持つ人の費用を挙げているのは、この部分の重さを示しているのだと思う[7]。

MITRE ATT&CK は、ルールの抜けを探す地図として使われている

MITRE ATT&CK は、実際に観測された攻撃者の戦術と技術をまとめた知識のベースだ[8]。2026年10月に出た版（v20）の企業向けのマトリクスには、偵察から影響までの15の戦術と、227のテクニック、479のサブテクニックがある。数は、僕が公開のデータから、取り消し・廃止されたものを除いて数えた[8]。

SIEM との関係は、主に二つある。一つは、ルールに ATT&CK の番号を付けることだ。先ほどの Wazuh のルール 40112 には T1078 と T1110 が付いていた[17]。Elastic の SSH のルールにも、総当たり、パスワードの推測、パスワードスプレー、正規のアカウントといった ATT&CK の項目が書かれている[18]。アラートが出たとき、それが攻撃のどの段階にあたるかが、番号から分かる。

もう一つは、抜けを探すことだ。自分の SIEM のルールを ATT&CK の表に重ねると、どの技術に検知があって、どこが空いているかが見える。Elastic の手引きも、足りないところを ATT&CK で探す段階を、検知の仕組みを育てる流れの中に置いている[23]。Wazuh のダッシュボードにも、ATT&CK の画面がある[6]。

ただ、表が埋まっていることと、検知できることは同じではない。ルールがあっても、必要なログが入っていなければ鳴らない。しきい値が環境に合っていなければ、鳴りすぎて読まれない。ATT&CK の検知の例が、使うログの種類と、調整する項目まで書いているのは、そこまでそろって初めて検知になるからだと思う[16]。

自分のラボで SIEM に触れる方法

試すのは、自分の環境の中だけにする

SIEM を学ぶなら、実際にログを流して、アラートが出るところを見るのがいちばん分かりやすい。ただ、試すのは自分が持っている環境の中だけにしている。他人のシステムやサービスに、許可なくログインを試したり、攻撃をまねた通信を送ったりすることは、日本では不正アクセス禁止法などに触れるおそれがある[30]。ここで挙げる方法も、自分のパソコンの中の仮想マシンか、自分で契約したクラウドの中で使う前提で書いている。

Wazuh は、ラボの組み方と検知の例を手引きに載せている

Wazuh は無料のオープンソースで、手引きに「概念実証（proof of concept）」のガイドがある。そこでは、ラボに仮想マシンを使い、最初の設定のすぐあとにスナップショット（その時点の状態の保存）を取って、試すたびにきれいな状態に戻すことを勧めている。小さなラボなら、中心の部品を1台にまとめた構成で足りるとしている[5]。

ガイドの中には、総当たりのログインの検知を確かめる例もある。自分で用意した端末どうしで認証の失敗を起こし、Wazuh が複数の認証の失敗をつなげてアラートにするところを見る、という流れだ[5]。表で見たような相関のルールが、自分の画面でどう鳴るかを確かめられる。

Elastic は、無料の機能の範囲でも検知ルールが入る

Elastic Security は Kibana に組み込まれていて、Elasticsearch と Kibana があれば使える[11]。検知ルールの公開のリポジトリの説明によると、Elastic Stack の標準の配布物に含まれる無料の機能の範囲でも、検知の画面を開けば最新のルールが入る[31]。どの機能が無料かは版とサブスクリプションで変わるので、使う前に公式の表で確かめることになる。

ルールの中身がリポジトリで公開されているのも、勉強には助かる。先ほどの SSH のルールのように、どんな条件で鳴るのかを、一行ずつ読める[18]。

Splunk には、無料の版と学習用のデータがある

Splunk には「Splunk Free」という無料の版がある。公式の説明では、1日に取り込めるのは500MBまでで、期限はない。ただし1台だけで動かす使い方に限られ、作ったアラートは動かない[32]。

学習用のデータもある。Splunk が公開している「Boss of the SOC（BOTS）」の第3版は、セキュリティの練習用のデータセットで、CTF の形で問題を解く使い方もできる。データは取り込み済みの形で配られていて、取り込みの量による制限を気にしなくてよいと説明されている。AWS の CloudTrail や VPC のフローログなど、クラウドのログも含まれている[33]。

攻撃の通信を自分で起こさずに、すでに記録されたログで調べる練習ができる。ログを読む練習としては、これがいちばん手軽だと思う。Splunk は、自分のクラウドの中に検知を試すための環境を組み立て、攻撃をまねて、そのログを Splunk に流す「Attack Range」も公開している[34]。こちらはクラウドの費用がかかり、使えるのは自分で契約した環境の中だけだ。

Windows のログオンを、図で見る

JPCERT/CC の LogonTracer は、Windows の Active Directory のイベントログから、ログオンに関わるイベントを読み、ホスト名（または IP アドレス）とアカウント名を結んでグラフにする道具だ。どのアカウントで、どの端末からログインが試されたかが、図で分かる[14]。SIEM そのものではないが、4624 や 4625 といったイベントが、つなげるとどう見えるかを学ぶのに向いている。

公的な資料は、この順で読むと全体がつながる

最後に、この記事で使った公的な資料を、僕が読んでつながりやすかった順に並べておく。どれも英語だ。

SIEM について調べるほど、道具の話は、ログと人の話になっていった。SIEM が見せてくれるのは、集めたログの中から、ルールが拾い上げたものだけだ。何を集め、何を怪しいと決め、鳴ったものをどう読むかは、使う側に残っている。

いま、あなたが守りたい環境で攻撃が始まっていたとしたら、それに気づくための記録は、どこに、どれだけ残っているだろうか。
