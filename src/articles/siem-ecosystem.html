「SIEM は、もう XDR に置き換わった」と言えるだけの調査は、僕が探した範囲の公的な資料には見つからなかった。似た名前の道具は、取って代わる関係というより、ログを渡し合い、重なり合う関係として説明されていた。

SIEM が何をする仕組みかは1本目に、検知のルールと SOC の仕事は2本目に書いた。この3本目は、SIEM のまわりの話だ。似た名前の道具との違い、主な製品、入れたあとに難しいこと、MITRE ATT&CK の使われ方、自分のラボで触れる方法、公的な資料を読む順番を扱う。製品は名前と種類だけを書き、比べて勧めることはしない。

確かさは、資料が公的な手引きか、公式の説明か、調査か、予測かと、資料の数から付けた目安。

SOAR・EDR・XDR・ログ管理と、どこが違うのか

セキュリティの道具は略語が多い。違いを、何を見て、何をするかで並べてみた。

似た名前の道具の違い（僕の整理）
名前主に見るもの主にすること
ログ管理あらゆるログ集めて、保存し、検索できるようにする
SIEM多くの機器の、セキュリティにかかわるログ形をそろえ、つなげて分析し、アラートを出し、保存する
SOARSIEM のアラートや、ログプレイブックに沿って、対応を自動にする（端末の切り離しなど）
EDRパソコンやサーバーの中の動き端末で怪しい動きを見つけ、その端末で対応する
XDR端末に加えて、ネットワーク・メール・クラウドなどいくつもの領域の検知と対応を一つにまとめる（範囲は製品ごとに違う）

ログ管理と SIEM の境目は、セキュリティのための分析をするかどうかにある。NIST の SP 800-92 が扱うのは、ログの管理全体の基盤づくりで[1]、SIEM はその上で、セキュリティのための分析とアラートを受け持つ。

SOAR は、SIEM の隣に置かれることが多い。実務者向けの手引きによると、SOAR の中には、自分でログを集めて分析するものもあれば、すでにある SIEM とつないで、その機能を使うものもある[2]。

EDR は、端末の中を深く見る道具だ。共同の手引きは、SIEM に入れるログの優先の最初に、EDR のログを置いていた[3]。ここで EDR と SIEM は取って代わる関係ではなく、EDR が SIEM にログを渡す関係として描かれている。

XDR は、端末の外まで検知と対応を広げる考え方だ。僕が読んだ範囲では、どこまでを XDR と呼ぶかは製品ごとに違い、一つの定義にまとまっていなかった。製品の側でも、境目は重なっている。Wazuh は自分を XDR と SIEM の機能を一つにした基盤だと説明し[4]、Microsoft Sentinel は、クラウドで動く SIEM で、SOAR の機能も持つと説明している[5]。

ここでは、勉強の中でよく名前を見る製品を、公式の説明に書かれた種類だけ並べる。どれが合うかは、組織の環境と、すでに使っている道具で変わる。

入れたあとに難しいのは、お金とデータと人だった

費用は、取り込む量で増えやすい

経営層向けの手引きは、SIEM と SOAR の費用として、製品の料金のほかに、人の費用を挙げている。専門の技能を持つ人を雇ってとどめる費用、いまいる人の技能を上げる費用と続けての訓練、外に任せるならその委託料だ。料金はデータの取り込みの量で決まる仕組みが多く、取り込みを管理しないと払いすぎる危険がある、とも書いている[10]。

一方で手引きは、適切に入れて動かす費用より、サイバーのインシデントが起きたときの費用のほうが、はるかに大きくなりうるとも書いている[10]。費用がかかるから何もしない、という読み方は、手引きの書き方とは違う。

データは、集めるより、正しく入り続けるほうが難しい

ログの取り込みは、一度つないだら終わりではない。機器の更新でログの形が変わる、エージェントが止まる、送り先の設定が消える。そうなっても、SIEM の画面には「何も起きていない」ように見える。アラートがないことと、何も起きていないことは違う。共同の手引きが、取り込みが正しく続いているかを定期的に確かめるよう勧めていた[3]のは、このためだと僕は読んでいる。

ルールを合わせる人は、組織の外から買ってきにくい

ルールを調整するには、その組織のふだんの姿を知っている必要がある。誰が夜中にサーバーへ入るのか、どのアプリケーションが変わった動きをするのか。製品の標準のルールは出発点で、組織に合わせる作業は、組織のことを知る誰かがすることになる。手引きが「入れたら終わり」ではないと書き、技能を持つ人の費用を挙げているのは、この部分の重さを示しているのだと思う[10]。

MITRE ATT&CK は、ルールの抜けを探す地図として使われている

MITRE ATT&CK は、実際に観測された攻撃者の戦術と技術をまとめた知識のベースだ[11]。2026年10月に出た版（v20）の企業向けのマトリクスには、偵察から影響までの15の戦術と、227のテクニック、479のサブテクニックがある。数は、僕が公開のデータから、取り消し・廃止されたものを除いて数えた[11]。

SIEM との関係は、主に二つある。一つは、ルールに ATT&CK の番号を付けることだ。2本目で見た Wazuh のルール 40112（失敗が続いたあとの成功）には、T1078 と T1110 が付いている[12]。Elastic の SSH のルールにも、総当たり、パスワードの推測、パスワードスプレー、正規のアカウントといった ATT&CK の項目が書かれている[13]。アラートが出たとき、それが攻撃のどの段階にあたるかが、番号から分かる。

もう一つは、抜けを探すことだ。自分の SIEM のルールを ATT&CK の表に重ねると、どの技術に検知があって、どこが空いているかが見える。Elastic の手引きも、足りないところを ATT&CK で探す段階を、検知の仕組みを育てる流れの中に置いている[14]。Wazuh のダッシュボードにも、ATT&CK の画面がある[4]。

ただ、表が埋まっていることと、検知できることは同じではない。ルールがあっても、必要なログが入っていなければ鳴らない。しきい値が環境に合っていなければ、鳴りすぎて読まれない。ATT&CK の検知の例が、使うログの種類と、調整する項目まで書いているのは、そこまでそろって初めて検知になるからだと思う[15]。

自分のラボで SIEM に触れる方法

試すのは、自分の環境の中だけにする

SIEM を学ぶなら、実際にログを流して、アラートが出るところを見るのがいちばん分かりやすい。ただ、試すのは自分が持っている環境の中だけにしている。他人のシステムやサービスに、許可なくログインを試したり、攻撃をまねた通信を送ったりすることは、日本では不正アクセス禁止法などに触れるおそれがある[16]。ここで挙げる方法も、自分のパソコンの中の仮想マシンか、自分で契約したクラウドの中で使う前提で書いている。

Wazuh は、ラボの組み方と検知の例を手引きに載せている

Wazuh の手引きには「概念実証（proof of concept）」のガイドがある。そこでは、ラボに仮想マシンを使い、最初の設定のすぐあとにスナップショット（その時点の状態の保存）を取って、試すたびにきれいな状態に戻すことを勧めている。小さなラボなら、中心の部品を1台にまとめた構成で足りるとしている[17]。

ガイドの中には、総当たりのログインの検知を確かめる例もある。自分で用意した端末どうしで認証の失敗を起こし、Wazuh が複数の認証の失敗をつなげてアラートにするところを見る、という流れだ[17]。2本目で見た相関のルールが、自分の画面でどう鳴るかを確かめられる。

Elastic は、無料の機能の範囲でも検知ルールが入る

Elastic Security は、Elasticsearch と Kibana があれば使える[7]。検知ルールの公開のリポジトリの説明によると、Elastic Stack の標準の配布物に含まれる無料の機能の範囲でも、検知の画面を開けば最新のルールが入る[18]。どの機能が無料かは版とサブスクリプションで変わるので、使う前に公式の表で確かめることになる。ルールの中身がリポジトリで公開されていて、どんな条件で鳴るのかを一行ずつ読めるのも、勉強には助かる[13]。

Splunk には、無料の版と学習用のデータがある

Splunk には「Splunk Free」という無料の版がある。公式の説明では、1日に取り込めるのは500MBまでで、期限はない。ただし1台だけで動かす使い方に限られ、作ったアラートは動かない[19]。

学習用のデータもある。Splunk が公開している「Boss of the SOC（BOTS）」の第3版は、セキュリティの練習用のデータセットで、CTF の形で問題を解く使い方もできる。データは取り込み済みの形で配られていて、取り込みの量による制限を気にしなくてよいと説明されている。AWS の CloudTrail や VPC のフローログなど、クラウドのログも含まれている[20]。

攻撃の通信を自分で起こさずに、すでに記録されたログで調べる練習ができる。ログを読む練習としては、これがいちばん手軽だと思う。Splunk は、自分のクラウドの中に検知を試すための環境を組み立て、攻撃をまねて、そのログを Splunk に流す「Attack Range」も公開している[21]。こちらはクラウドの費用がかかり、使えるのは自分で契約した環境の中だけだ。

Windows のログオンを、図で見る

JPCERT/CC の LogonTracer は、Windows の Active Directory のイベントログから、ログオンに関わるイベントを読み、ホスト名（または IP アドレス）とアカウント名を結んでグラフにする道具だ。どのアカウントで、どの端末からログインが試されたかが、図で分かる[22]。SIEM そのものではないが、4624 や 4625 といったイベントが、つなげるとどう見えるかを学ぶのに向いている。

SIEM について調べるほど、道具の話は、ログと人の話になっていった。SIEM が見せてくれるのは、集めたログの中から、ルールが拾い上げたものだけだ。何を集め、何を怪しいと決め、鳴ったものをどう読むかは、使う側に残っている。

自分のラボに SIEM を1台置くとしたら、あなたは最初にどのログを流し、何が鳴るところを見てみたいだろうか。
