認証は、ログインしようとしている相手が、登録した本人と同じ秘密や機器を持っているかを確かめることで、多要素認証（MFA）は、種類の違う二つ以上の要素で確かめる。MFA の中にも強さの差があり、手で打ち込む確認コードは偽のサイトに中継されうるが、WebAuthn の鍵はサイトの名前に結びつくので中継では使えない。オリジンと証明書は TLS の記事に、ログインのあとの Cookie は HTTP の記事に書いた。

認証は、知っているもの・持っているもの・本人であることの三つで確かめる

NIST の SP 800-63B（2025年の第4版）は、認証の要素を「知っているもの」「持っているもの」「本人であること」の三つとしている[1]。パスワードと PIN は知っているもの、ワンタイムパスワードを出すアプリや機器、セキュリティキーは持っているもの、指紋や顔は本人であることに当たる。

多要素認証は、違う種類の要素を二つ以上確かめる。パスワードを二つ聞いても、要素は一つのままだ。SP 800-63B-4 は、二つの要素を求める水準（AAL2）のサービスに、フィッシングに強い方法を選べるようにしておくことを求めている[1]。

生体は単独では使わない。SP 800-63B-4 は、生体を、持っているもの（機器）と組み合わせる多要素の一部としてだけ認める。照合が確率で決まることと、顔の写真や物に残った指紋のように、生体が秘密ではないことが理由だ。指紋や顔は、機器の中の鍵を使えるようにする「起動の要素」として使う[1]。

パスワードは、長さと漏えいの照合で選ばせ、定期変更を求めない

SP 800-63B-4 のパスワードの決まりは、複雑さより長さと照合を重く見る[1]。

  • パスワードだけで認証するなら15文字以上、多要素の一部なら8文字以上を求める。64文字以上まで受け付けるのがよいとしている
  • 大文字・数字・記号を混ぜるような組み立ての決まりを課さない
  • 定期的な変更を求めない。漏れた形跡があるときは変えさせる
  • 新しいパスワードを、過去に漏えいしたもの・辞書の言葉・サービス名やユーザー名から作った言葉の一覧（ブロックリスト）と照らし、載っていれば理由を示して選び直させる
  • 秘密の質問とヒントを使わせない。パスワードマネージャーと貼り付けを許す
  • 失敗の回数を制限する

付録は、組み立ての決まりを課すと、「password」が「Password1!」になるような予測しやすい変え方が起きると説明している[1]。攻撃する側は、前の漏えいで当たったパスワードから試すので、一覧との照合のほうが効く。

パスワードは、ソルトを付けた遅いハッシュで保存する

サーバーはパスワードそのものを保存せず、ハッシュにして保存する。ハッシュは一方向の計算で、値から元のパスワードには戻せない。暗号化は鍵があれば元に戻せるので、パスワードの保存には向かない[2]。

ソルトは利用者ごとに変える乱数で、パスワードと一緒にハッシュにかける。同じパスワードでも値が変わるので、前もって計算した表が使えず、攻撃する側は一件ずつ計算することになる[2]。SP 800-63B-4 は、32ビット以上のソルトを、ハッシュの値と一緒に保存するよう求めている[1]。

SHA-256 のような速いハッシュは、盗まれたハッシュに対して、推測を速く大量に試させてしまう。OWASP は、Argon2id（メモリ 19MiB・2回・並列1 以上）を第一に、使えなければ scrypt、古いシステムでは bcrypt、FIPS 140 への適合が要るなら PBKDF2-HMAC-SHA256 を60万回以上、と勧めている[2]。SP 800-63B-4 も、計算の重さを性能の許す限り高くすることと、サーバーだけが持つ鍵でもう一段かけること（OWASP の言う「ペッパー」）を勧めている[1][2]。

ワンタイムパスワードは、共有した鍵と、回数か時刻から作る

HOTP（RFC 4226）は、サーバーと機器が同じ秘密の鍵とカウンター（回数）を持ち、HMAC-SHA-1 の結果を切り詰めて6桁以上の数字にする。カウンターがずれたときのために、サーバーは先の数個の値まで照らす。照らす幅を広げるほど当てられやすくなるので、失敗の回数の制限を合わせて置く[3]。

TOTP（RFC 6238）は、カウンターの代わりに時刻を使う。既定では、1970年1月1日からの秒数を30で割った整数を、HOTP のカウンターとして使う。同じ30秒の中では同じ値になるので、一度通ったコードを二度目は受け付けない。通信の遅れには一つ前の区切りまで認めることを勧め、幅を広げるほど攻撃の余地も広がるとしている。HMAC-SHA-256 と HMAC-SHA-512 も使える[4]。

OTP は使い回せない点で、パスワードより強い。ただ SP 800-63B-4 は、手で打ち込む方法をフィッシングに強いとは見なさない。打ち込んだ値がその接続に結びついていないので、偽のサイトが受け取って、そのまま本物に渡せるからだ[1]。

SMS のコードは、電話網を通るので「制約つき」とされている

SP 800-63B-4 は、SMS や音声通話でコードを送る方法を「制約つき」の認証方式としている。使う組織は、リスクを評価して受け入れ、制約のない別の方法も用意する[1]。電話番号の登録や変更は、新しい認証器を結びつけるのと同じ扱いで、コードを送る前に、端末の入れ替え・SIM の変更・番号の移転のような兆しを見るよう勧めている[1]。

MITRE ATT&CK は、SMS で送るコードが途中で盗まれうることと、SMS を送る事業者が狙われた例を挙げている[5]。CISA の Microsoft Entra ID の設定の基準（SCuBA）は、SMS・音声通話・メールの OTP を最も弱い方法とし、無効にするよう求めている[6]。

プッシュ通知の承認は、繰り返し送られると押されてしまう

通知の「承認」を押すだけの方法では、パスワードを手に入れた攻撃者がログインを繰り返し、通知を何度も送りつけられる。利用者が根負けして承認するのを待つ手口を、MITRE ATT&CK は「Multi-Factor Authentication Request Generation」（T1621）としてまとめ、「MFA 疲れ」と呼んでいる[7]。

対策は、承認に数字の入力を足すことだ。ログインの画面に出た数字をアプリに打ち込ませると、その画面を見ていない人は承認できない（番号の照合）。CISA は2022年10月の資料で、番号の照合を、フィッシングに強い MFA をすぐに入れられない組織の当座の対策として勧めている[8]。Microsoft Authenticator では、すべてのプッシュ通知で番号の照合が有効になっている[9]。

SP 800-63B-4 は、二つの画面の値を見比べて承認するだけの方式を、もう受け入れない。見比べずに承認されやすく、MFA 疲れの攻撃で実際に起きたためで、値を一方の画面からもう一方へ打ち込ませる形を求めている。送る通知の数に上限を置くことも勧めている[1]。ATT&CK も同じ上限を対策に挙げている[7]。

フィッシングに強い認証は、鍵をサイトの名前に結びつける

SP 800-63B-4 は、フィッシングへの強さを「利用者の注意に頼らずに、偽の相手へ秘密や有効な出力を渡さない」性質と定め、暗号の鍵で認証する方式でなければ満たせないとしている。その例に、FIDO2 の認証器が使う WebAuthn を挙げている[1]。

WebAuthn（W3C）では、登録のときに認証器がサイトごとに新しい鍵の組を作る。秘密鍵は認証器が持ち、誰にも見せない前提で、サイトは公開鍵だけを保存する[10]。鍵には、サイトの識別子（RP ID。example.com のようなドメイン）が結びつく。ブラウザーは、開いているページのオリジンが https で、そのドメインが RP ID と同じか、その下にあるときにだけ、その鍵を使わせる[10]。

ログインでは、サイトが毎回、乱数（チャレンジ）を送る。ブラウザーは、チャレンジとページのオリジンを書いたデータ（clientDataJSON）を作り、認証器は、RP ID のハッシュを含むデータと一緒に秘密鍵で署名する。サイトは公開鍵で署名を確かめ、チャレンジとオリジンが予想どおりかを確かめる[10]。

偽のサイト（example.net）が本物（example.com）のふりをしても、ブラウザーは example.com の鍵を example.net では使わせない。中継しても、署名したデータの中のオリジンが本物と違うので、本物のサイトは受け付けない。打ち込むコードと違い、利用者が偽物に気づかなくても防げる。CISA も FIDO/WebAuthn を、広く使えるフィッシングに強い認証として挙げている[11]。

パスキーは、WebAuthn の仕様で、ユーザー名を先に入れなくても使える「見つけられる認証情報」の呼び名だ[10]。端末のあいだで同期するパスキーもある。SP 800-63B-4 は、同期できる鍵を取り出せる鍵として扱い、最も高い水準（AAL3）では使わせない[1]。

認証の方法と、偽のサイトへの中継（SP 800-63B-4 と WebAuthn から）
方法要素偽のサイトに中継されうるか
パスワード知っているものされうる。あとで使い回せる
SMS のコード持っているもの（制約つき）されうる。電話網の側でも盗まれうる
TOTP・HOTP持っているものされうる。使い回しはできない
番号の照合つきプッシュ持っているものされうる。手で打ち込む方法なので
WebAuthn・パスキー持っているもの（PIN や生体で起動）されない。署名にオリジンが入る

MFA を通ったあとは、Cookie と、MFA を通らない入口が狙われる

ログインが終わると、サーバーはセッションの Cookie を渡し、それを見せる要求を本人として扱う（HTTP の記事）。SP 800-63B-4 は、Cookie を認証器ではなくセッションの間だけの秘密とし、Secure を必須に、HttpOnly と SameSite（Lax か Strict）を勧めている[1]。

MITRE ATT&CK は、盗んだセッションの Cookie を使うと、認証を経ずにログインした状態になり、一部の MFA を素通りできると書いている。偽のサイトで通信を中継し、ログインのあとの Cookie を集める道具があることも挙げている[12]。WebAuthn ではオリジンが合わず、中継したログインが通らないので、この手口への備えになる。端末の中から盗まれる場合に向けて、SP 800-63B-4 は、Cookie を持っていることを暗号で示す新しい仕組み（DBSC）に触れている[1]。

MFA をかけていない入口があれば、そこから入られる。2026年11月6日、CISA は SonicWall の SonicOS の SSL VPN の脆弱性 CVE-2026-19868 を、悪用が確かめられた脆弱性の一覧（KEV）に加えた。別の認証方式の正しい認証情報を持つ利用者が、SAML の認証と、SAML で求めている MFA を回避できるおそれがあるという内容で、影響を受けるのは Gen7 の 7.3.3-7015 以前と Gen8 の 8.2.2-8015 以前だ[13][14]。対処は、メーカーの告知（SNWLID-2026-0014）に沿って修正を当てることだ[13]。

ログでは、失敗の連続、拒否の連続、合わない場所を見る

認証のログ（ID の基盤、VPN、サーバーのログオンの記録）では、次の並びを見る[1][7]。

  • 一つのアカウントへの失敗の連続。SP 800-63B-4 は、一つの認証器への連続の失敗を100回以下で止めるよう求め、IP アドレス・場所・要求の時刻の並びで、普段と違う動きを見分ける方法も挙げている[1]
  • 多くのアカウントへの、同じ少数のパスワードでの失敗。パスワードスプレーと呼ばれ、ロックアウトや検知を避けるため、わざとゆっくり試すこともある[15]。アカウントごとの回数だけを見ていると見逃す
  • パスワードは通ったのに、MFA の拒否や時間切れが続く。パスワードが漏れていて、MFA 疲れを狙われている兆しだ。ATT&CK は、普段と違う送り元からの MFA の要求の多さと、拒否や時間切れになった要求を見るよう挙げている[7]。CISA も、拒否された通知を調べるよう勧めている[8]
  • 合わない場所。ログインの送り元が見慣れない国や IP アドレスで、MFA の端末の場所と合わない[7]
  • MFA の方法の新しい登録や、MFA の対象からの除外。入り込んだ攻撃者が、自分の方法を登録したり、MFA を外したりする手口がある[16]

架空の例では、user01 に 203.0.113.45 から、数分のうちにパスワードの成功と MFA の拒否が10回続き、そのあと承認された並びがこれに当たる。本人への確認、パスワードの変更、セッションの取り消しへ進む。

自分の環境で確かめる

試すのは、自分の機械と許可された演習の環境だけにする。他人のサービスにログインを試したり、通知を送らせたりはしない。

TOTP は、Python の標準ライブラリ（hmac・hashlib）だけで計算できる。RFC 6238 の付録 B の試験値では、鍵を文字列「12345678901234567890」、時刻を59秒としたとき、SHA-1 の8桁で 94287082 になる[4]。59 を30で割った 1 を8バイトにして HMAC-SHA-1 にかけ、RFC 4226 の切り詰め（最後の1バイトの下4ビットを位置にして4バイトを取り出し、先頭のビットを落とす）をして、1億で割った余りを取ると、この値と一致する[3][4]。

保存の違いは hashlib.pbkdf2_hmac で見られる。同じパスワードに、os.urandom(16) で作った別々のソルトを渡すと、違う値になる。回数を60万にすると、SHA-256 を1回かけるより桁違いに時間がかかる。Python の説明書も、パスワードのハッシュは調整でき、遅く、ソルトを含むものでなければならないとしている[17]。

WebAuthn は https のほか、http://localhost でも使える[10]。自分のパソコンで動かしたページで navigator.credentials.get() を呼び、返ってきた clientDataJSON を文字に戻すと、type（webauthn.get）・challenge・origin が入っている[10]。
